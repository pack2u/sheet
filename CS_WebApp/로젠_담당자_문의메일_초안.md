### 1. 호출자 IP 검증 — 가장 급한 사항

당사 CS 시스템은 **Google Apps Script 기반 웹앱**입니다.
이 환경은 외부 API 호출 시 발신 IP가 Google 공용 대역에서 **유동적으로 배정**되어,
특정 IP를 고정 등록하는 것이 불가능합니다.

아래 중 가능한 방식이 있는지 확인 부탁드립니다.

- ① 인증키(secretKey)만으로 인증하고 **IP 검증을 면제**받는 방식
- ② **IP 대역(CIDR) 단위** 등록이 가능한지
- ③ 위 둘이 모두 불가하다면, 고정 IP를 보유한 **중계 서버를 별도 구축**해야 하는지

③이라면 당사가 서버를 세워야 하므로 일정이 달라집니다.
**이 답변 하나로 착수 시점이 정해지므로** 우선 회신 부탁드립니다.

### 3. userId(연동업체코드) 확인

API Docs에 *"연동업체코드가 아닌 경우 거래처코드 입력"* 으로 안내되어 있습니다.
당사는 별도 연동업체를 통하지 않고 **화주사가 직접 개발**하는 형태입니다.

- `userId` 에 당사 거래처코드(30556066)를 입력하는 것이 맞는지
- 연동업체코드가 별도로 발급되는 것이라면 그 발급 절차

확인 부탁드립니다.

### 4. 반품(회수) 접수 — 구현하며 확정하지 못한 부분

당사는 고객이 반품을 요청하면 CS 화면에서 바로 회수 접수를 넣는 흐름으로
`registReturnRequest` 를 붙였습니다. 그 과정에서 아래가 문서만으로는 확정되지 않았습니다.

**(1) 운임(`dlvFare`)을 무엇으로 넣어야 하는지**

`dlvFare` 는 `null` 또는 `0` 이 불가한 필수값입니다.
당사는 값을 임의로 정하지 않기 위해, 접수 직전에 `reverseChkInfoMulti` 를 호출해
해당 원송장의 `fareTy` 와 `dlvFare` 를 받아 **그대로** 사용하도록 구현했습니다.

- 이 방식이 맞는지 (계약운임과 일치하는 값인지)
- 아니라면 어느 값을 기준으로 넣어야 하는지

**(2) 운임타입(`fareTy`) 제한**

2026.04.29 자로 **선불(010)·착불(020)** 만 허용되는 것으로 확인했습니다.
당사 계약 기준으로 반품 접수 시 적용 가능한 운임타입이 무엇인지 확인 부탁드립니다.
(현재 구현은 010·020 이 아닌 값이 조회되면 **접수를 보류하고 담당자에게 알리도록**
해 두었습니다. 임의로 바꿔 넣지 않기 위함입니다.)

**(3) 집하 희망일 지정 가능 여부**

`registReturnRequest` 요청 필드에 집하 희망일에 해당하는 항목이 보이지 않습니다.

- 접수 시점 기준으로 **언제 집하**되는지 (당일/익일)
- 집하일을 지정할 방법이 있는지, 없다면 마감 시각이 있는지

고객에게 안내해야 하는 값이라 확인이 필요합니다.

**(4) 반품 운송장번호(`slipNo`)를 언제 받을 수 있는지**

`registReturnRequest` 응답은 `takeNo`(접수번호)를 주고,
`slipNo` 는 `inquiryReturnStateMulti` 로 조회하는 것으로 이해했습니다.

- 접수 직후 바로 조회되는지, 아니면 일정 시간 뒤인지
- 조회 가능해지기까지 **권장 대기 시간 또는 폴링 주기**

당사 반품대장에 회수 송장번호를 적어야 하므로, 접수와 조회 사이 간격을 알아야
설계가 확정됩니다.

**(5) 접수 취소 응답의 상태코드**

`cancelReserveState` 응답은 `resvStat = 030` 을 반환한다고 되어 있으나,
조회 API의 상태 코드표에는 **`20 = 접수취소`** 로 적혀 있어 값과 자릿수가 다릅니다.

- 두 값이 **서로 다른 체계**가 맞는지
- 같은 것이라면 어느 쪽이 정확한지

혼동을 피하기 위해 현재 구현은 취소 응답의 코드를 해석하지 않고 성공 여부만
판단하도록 해 두었습니다.

### 5. `resultCd` 성공값이 API마다 다른 점

개발가이드 기준으로 성공값이 아래처럼 섞여 있습니다.

| 성공값 | 해당 API |
|---|---|
| `TRUE` / `FALSE` | 화물추적, 반품 전 API 등 대부분 |
| `SUCCESS` / `FAIL` | `contPickFares`, `contRtnFares` |
| `SUCCESS` / `FALSE` | `integratedInquiry` |

- 이 차이가 **의도된 것**인지, 문서상 오기인지
- 향후 통일 계획이 있다면 그 시점

당사는 우선 `TRUE`·`SUCCESS` 를 모두 성공으로 보도록 구현했습니다.
통일 계획이 있다면 미리 알려주시면 반영하겠습니다.

### 6. 화물상태(`statNm`) 값 목록

화물추적 조회 응답의 `statNm` 이 코드가 아닌 **한글 문자열**로 내려옵니다.

- 현재 사용 중인 **상태 문자열 전체 목록**을 받을 수 있는지
- 향후 문구가 변경될 경우 **사전 공지**가 이루어지는지

당사 시스템에서 배송 완료 여부를 판정하는 유일한 기준이라 목록 확보가 필요합니다.
문구가 바뀌면 판정이 조용히 틀어지므로 사전 공지 여부가 특히 중요합니다.

### 7. 개발계(topenapi) 테스트 범위

당사 거래처코드로 **개발계에서 화물추적·반품 API 테스트가 가능한지** 궁금합니다.

개발계에 당사 실데이터가 없거나 별도 **연계 등록**이 필요한 API가 있다면
해당 절차를 미리 안내해 주시기 바랍니다.
테스트코드로만 호출 가능한 API가 있다면 그 부분도 함께 알려주시면 감사하겠습니다.

### 8. 일일 호출 한도

개발가이드에 호출 건수 제한이 명시되어 있지 않습니다.
**일일 또는 분당 호출 상한**이 있는지, 있다면 초과 시 동작(차단 또는 지연)이
어떻게 되는지 알려주시면 캐싱 설계에 반영하겠습니다.
(현재는 상한을 모르는 상태라 자체적으로 보수적인 캐시를 두고 있습니다.)
