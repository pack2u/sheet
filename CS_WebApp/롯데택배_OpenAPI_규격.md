| 운영 | https://apipt.llogis.com:20100/accounts/login | 124.243.74.30 |

### API HOST (실제 호출 대상)

| 환경 | URL |
|---|---|
| 테스트 | `https://devapigw.llogis.com:10100` |
| 운영 | `https://apigw.llogis.com:10100` |

포털(20100)과 API 게이트웨이(10100)는 **호스트도 포트도 다르다.** 혼동 주의.

### 인증

- 모든 API가 JWT 기반 인증 요구.
- 헤더: `Authorization: IgtAK <클라이언트키>`
  (`IgtAK` + 공백 한 칸 + 포털에서 발급받은 키)
- `Invalid Token Error` 응답 = 키가 틀렸거나 형식이 틀린 것.
- **환경별로 계정과 키를 따로 발급받아야 한다.** 개발키로 운영 호출 불가.

> ⚠️ **`Key` 와 `Secret` 은 다른 값이다.** 어플리케이션 화면에는 `Secret` 과 `Key` 가
> 따로 있는데, `Authorization` 헤더에 넣는 것은 **`Key`(클라이언트키)** 다.
> `Key` 는 `키발급` 버튼을 눌러야 생성된다 — 앱을 등록만 하면 비어 있다.

### 공통 규약

- 요청/응답 포맷 `application/json`, 인코딩 **UTF-8** 고정.
- 성공/실패 판단은 **HTTP status code** 기준.
- 필드 길이 제한은 전부 **UTF-8 byte** 기준 (한글 3byte).
- **리스트 전송은 1회 100건까지.**

## 2. 이용 절차

```
회원가입 → 어플리케이션 등록 → 권한추가(RS_ADDR) → 키발급 → API 이용
```

1. 포털 회원가입 후 로그인
2. `/app/register` 에서 어플리케이션 등록 — **접속허용 IP는 필수가 아님**
3. `[설정]-[권한]` 탭 → 허용 권한에서 **`RS_ADDR`** 체크 → `권한 추가`
4. `[설정]-[고급]` 탭 → `키발급` 버튼 → API Key 생성
5. API 호출

> **`RS_ADDR` 권한 하나로 자체출력 + 출고/반품 지시 연동이 모두 가능하다.**

### ★ 우리에게 중요한 두 가지

- **접속허용 IP가 필수가 아니다** → Apps Script(고정 IP 없음)에서 `UrlFetchApp` 직접 호출이 가능하다. 중계 서버가 필요 없다.
- 개발 환경 어플리케이션은 등록 완료 (아래).

### 우리 어플리케이션 (개발 환경)

| 항목 | 값 |
|---|---|
| 이름 | CS앱 |
| 애플리케이션 ID | `C011308` |
| **거래처코드** (`jobCustCd` / 주소정제 `id`) | **`348782`** |
| 인증 타입 | 서버 |
| 접속허용 IP | **비워 둘 것** — 채우면 Apps Script(고정 IP 없음)에서 전부 차단된다 |
| 권한 | `RS_ADDR` (주소 정제 & 온라인주문) |
| Key (클라이언트키) | `_secrets.gs` 의 `LOTTE_API_KEY_DEV` — **git 추적 안 됨** |
| 쿼터 적용 | `Y` |
| 쿼터 | **10000** |

> **쿼터 10,000건은 "일" 단위다** (롯데 전산 담당자 회신, 2026-08-31).
> 하루 10,000회. CS 조회량 기준으로는 여유가 있지만, 화면을 새로고침할 때마다
> 호출하면 금방 는다. **응답 캐싱(`CacheService`)을 전제로 설계할 것.**
> 쿼터 부족 시 포털에 `쿼터 추가 요청` 버튼이 있다.

## 2-1. 실호출 검증 결과 (2026-08-31, 개발 환경)

| 확인 항목 | 결과 |
|---|---|
| `devapigw.llogis.com:10100` 도달 / TLS | ✅ 정상 |
| 비표준 포트 10100 | ✅ 문제 없음 |
| `Authorization: IgtAK <Key>` 헤더 형식 | ✅ 맞음 (아래 대조군으로 확인) |
| 주소정제 단건 호출 | ✅ **200 OK, `result:success`** — `id`(거래처코드) 값과 무관하게 동작 |
| 표준 화물추적 (테스트 거래처 `101000`) | ✅ **200 OK, 추적 이력 수신** |
| 표준 화물추적 (우리 거래처 `348782`) | ❌ **차단 — 화물추적 연계 등록 필요** |

### ★ 화물추적은 거래처 단위 "연계 등록"이 별도로 필요하다 (확정)

`RS_ADDR` 권한만으로는 부족하다. **같은 운송장번호인데 거래처코드에 따라 갈린다.**

```
화물추적 cust=101000 inv=313633845254 → code:S  정상 조회
화물추적 cust=348782 inv=313633845254 → code:E  영업담당자에게 문의하여 화물추적 연계 등록을 해주시기 바랍니다.
주소정제 id=101000 / 348782 / 공란     → 전부 success   (주소정제는 거래처코드를 검증하지 않는다)
```

> 처음엔 테스트 거래처 `101000` 로만 호출해 보고 "연계 등록이 불필요하다" 고 판단했는데,
> **`101000` 이 이미 등록돼 있어서 통과한 것**이었다. 우리 거래처코드로 바꾸자 바로 막혔다.
> 개발 환경조차 뚫리지 않으므로 **연계 등록 전에는 화물추적 연동을 진행할 수 없다.**

**응답 (화물추적·주소정제 둘 다 동일)**

```json
{"code":"EGTA4011","message":"IGateActivityException: Invalid Token Error [C011308,apiClient is null forC011308]"}
```
→ HTTP 500

**대조군 — 헤더를 아예 빼고 호출**

```json
{"code":"EGTA4011","message":"IGateActivityException: Invalid Token Error [Authorization : IgtAK {ClientKey) 입력이 필요 합니다.]"}
```

두 메시지가 다르다는 점이 핵심이다. 헤더를 넣었을 때는 게이트웨이가 **앱 `C011308` 을 식별했고**,
막힌 이유는 키가 아니라 `apiClient is null` — 즉 **해당 앱에 API 권한이 붙어 있지 않다.**

> ### `EGTA4011` 해석표
> | message 꼬리 | 의미 | 조치 |
> |---|---|---|
> | `Authorization : IgtAK {ClientKey) 입력이 필요 합니다.` | 헤더 없음/형식 오류 | `IgtAK` + 공백 + Key |
> | `apiClient is null for<앱ID>` | 앱에 권한 미부여 **또는 권한 추가 전에 발급된 키** | 아래 참조 |
>
> FAQ는 `Invalid Token Error` 를 "API Key가 잘못된 경우"로만 설명하지만,
> 실제로는 **권한 문제도 같은 코드로 떨어진다.**

### ★ 권한 추가는 게이트웨이에 즉시 반영되지 않는다

실제로 겪은 일 (2026-08-31, 개발 환경):

1. 앱 등록 → 키발급 → 호출 → `apiClient is null`
2. `[설정]-[권한]` 에서 `RS_ADDR` 추가 (`애플리케이션 권한` 에 등재된 것 확인) → 재호출
3. **여전히 `apiClient is null`** — 화면상 권한은 붙어 있는데도 그대로였다
4. 몇 분 뒤 아무것도 바꾸지 않고 재호출 → **200 OK**

> **키 재발급은 필요 없었다.** 권한 추가 전에 발급받은 키가 그대로 동작한다.
> `apiClient is null` 이 권한을 붙인 직후에도 나온다면 **키를 다시 발급하지 말고
> 몇 분 기다렸다가 재시도할 것.** 게이트웨이가 권한 정보를 캐싱하는 것으로 보인다.
>
> (이용안내가 `권한추가 → 키발급` 순서인 것은 맞지만, 순서를 어겨도 키를 다시 받을
> 필요는 없다. 위 3번에서 순서 문제로 오판하기 쉬우니 주의.)

## 3. APIs (B2C)

### 3.1 주소정제 (출력정보 조회) — 단건

`POST /api/address/newprint-info`

주소 유효성 검증 + 운송장 자체출력에 필요한 분류정보 획득용.

**Request**

| Path | Type | 필수 | 설명 |
|---|---|---|---|
| `id` | String(6) | | 거래처코드 (6자리 택배코드) |
| `network` | String(2) | ✅ | 서비스구분 `00` 고정 (00:일반 / 01:특화) |
| `area_no` | String(5) | ✅ | 도착지 기초구역번호 (5자리 우편번호) 예 `04527` |
| `zip_no` | String(6) | ✅ | 도착지 구우편번호 (6자리) 예 `100801` |
| `address` | String(500) | ✅ | 도착지 주소 (실제 배달 주소) |
| `pick_area_no` | String(5) | ✅ | 출발지 기초구역번호 |
| `pick_zip_no` | String(6) | | 출발지 구우편번호 |
| `pick_address` | String(500) | ✅ | 출발지 주소 (실제 집하 주소) |
| `spcalShopNm` | String(100) | | 특화매장명 (수하인명) |
| `tel` | String(14) | | 특화매장 전화번호 (수하인 전화번호) |

**Response** (🖨️ = 운송장 인쇄에 쓰이는 항목)

| Path | Type | 설명 |
|---|---|---|
| `result` | String(50) | `success` / `error` |
| `message` | String(500) | 오류메시지 (실패시) |
| `city_gun_gu` | String(100) | 🖨️ 시군구 |
| `dong` | String(100) | 🖨️ 읍면동 |
| `area_no` | String(5) | 정제된 기초구역번호 |
| `zip_no` | String(6) | 정제된 6자리 우편번호 |
| `filt_cd` | String(50) | 🖨️ 도착지코드 (CODE39 바코드) 길이 3~4 |
| `tml_cd` | String(50) | 🖨️ 노선구분 — `■`선분류 / `★`직노선 / 공백·`1`·`A` 기타. 공백도 정상 |
| `tml_nm` | String(50) | 🖨️ 분류코드 예 `F-◆H2-장48` |
| `air_fare` | String(15) | 항공료 |
| `ship_fare` | String(15) | 도선료 |
| `brnshp_cd` | String(5) | 배송대리점코드 |
| `brnshp_nm` | String(100) | 🖨️ 배송대리점명 |
| `emp_nm` | String(100) | 🖨️ 배송기사명 예 `장48-김롯데` |
| `bld_annm` | String(200) | 배송주소지 건물별칭 |
| `lttd` / `lgtd` | String(20) | 배송주소지 건물 위도 / 경도 |
| `dlv_msg` | String(600) | 배달가능여부메시지 예 `[배송불가]` |

**요청 예제**



### 화물상태 코드표 (`godsStatCd`)

롯데 전산 담당자 회신 (2026-08-31) — API 문서에는 없고 별도로 받은 표다.

| 코드 | 상태명 | 배송 흐름 |
|---|---|---|
| `12` | 운송장등록 | 접수 |
| `10` | 집하 | 발송인에게서 수거 |
| `20` | 발송 | 터미널 출발 |
| `21` | 도착 | 터미널 도착 |
| `40` | 배달전 | 기사 배송 출발 |
| `41` | **배달완료** | 완료 |
| `09` | 취소 | — |

> **회신 원문: "코드는 통보 없이 추가 될 수 있습니다."**

#### ⚠️ 이 표는 완전하지 않다 — 코드로 하드코딩하지 말 것

우리가 실제로 받은 응답에 **`02`(출력) 이 들어 있는데 위 표에는 없다.**

```
tracking[0]  godsStatCd 02  godsStatNm 출력   "운송장 출력을 하였습니다."
tracking[1]  godsStatCd 10  godsStatNm 집하   "물품을 보내셨습니다."
```

따라서 구현 원칙은 이렇다.

1. **표에 없는 코드가 온다고 전제한다.** 매핑에 없으면 응답의 `godsStatNm` /
   `status` 를 그대로 보여준다. 절대 "알 수 없음" 으로 뭉개지 말 것.
2. 완료 판정은 `41` 하나만 신뢰한다.
3. 표시용 문구는 `status` 필드가 이미 사람이 읽는 문장이라 그대로 쓰면 된다.

#### 사고 관련 코드는 없다

코드표에 사고·파손·분실·반송에 해당하는 코드가 **없다**(`09` 취소가 전부).
**화물추적으로는 사고 건을 판별할 수 없다**는 앞선 결론이 코드표로 확정됐다.
사고는 ALPS 화면에서만 확인 가능하다.

#### 필드명 주의

**실제 JSON 응답 필드는 `godsStatCd` / `godsStatNm`** 다 (`o` 가 하나 더 있다).

### ★ 택배사고 조회 가능 여부 (2026-08-31 조사)

**결론: 사고 접수 내용을 받아오는 API는 이 포털에 없다.**

- API 문서 전문(98KB)에 **"사고" 라는 단어가 한 번도 나오지 않는다.**
- 제공 API는 주소정제(2) · 주문접수 · B2B(2) · 화물추적, **총 5종이 전부**다.
- 어플리케이션 `허용 권한` 목록에 있는 리소스도 `RS_ADDR`(주소 정제 & 온라인주문) **하나뿐**이다.

사고 정보에 닿을 수 있는 **유일한 통로는 화물추적의 상태값**이다.

| 필드 | 성격 |
|---|---|
| `tracking[].godsStatCd` / `godsStatNm` | 화물상태 코드 / 명 |
| `tracking[].status` | 화물상태 문구 (사람이 읽는 문장) |
| `result[].cdNm` | 요약 코드명 |

그러나 **`godsStatCd` 전체 코드표가 문서에 없다.** 개발 샘플에서 실제로 관측된 값은
`02`(출력), `10`(집하) 둘뿐이라 사고 상태가 이 코드 체계에 포함되는지 확인할 수 없었다.

> 설령 포함되더라도 화물추적이 주는 것은 **"사고 상태"** 지
> **"사고 접수 내용"**(사고 원인, 처리 경과, 보상 협의 내역)이 아니다.

#### 사고 기능은 ALPS 웹 화면에만 있다

ALPS(<https://partner.alps.llogis.com/>) `화물사고서비스` 메뉴에 아래가 있다.
**전부 화면 기능이고, 대응하는 OpenAPI는 없다.**

| ALPS 메뉴 | OpenAPI |
|---|---|
| 화물사고관리 → 화물사고 확인서 조회 | ❌ 없음 |
| 화물사고관리 → 화물사고접수등록(거래처) | ❌ 없음 |
| 화물사고관리 → 화물사고진행현황상세 | ❌ 없음 |
| 택배용품관리 → 발주접수 / 발송관리 | ❌ 없음 |

**따라서 사고 건은 당분간 자동화 대상이 아니다.** 현실적인 선택지는 둘이다.

1. **딥링크 (권장·단기)** — CS 화면에서 송장번호를 들고 ALPS 해당 화면으로 바로 넘긴다.
   API가 필요 없고 CS의 화면 전환 비용만 줄인다. `화물사고진행현황상세` 의 URL 패턴 확보 필요.
2. **정식 요청 (중기)** — 담당자에게 사고 조회 API 제공을 요청한다.

> ALPS 화면을 스크래핑하는 방식은 권하지 않는다. 세션·화면 구조에 의존해 쉽게 깨지고,
> Apps Script 에서 로그인 세션을 유지하기도 어렵다.

**담당자에게 물어야 할 것 (김준수 대리):**

1. **`godsStatCd` 전체 코드표** — 사고/미배달/파손/분실 관련 코드가 있는지.
   코드표 없이는 상태 판정 로직을 짤 수 없으므로 어차피 필수다.
2. 사고 접수 내역 조회 API의 **제공 계획 여부**
3. **우리 `jobCustCd`(업무거래처코드)** — 아래 참조

### ★ 테스트 거래처코드로는 우리 화물이 안 보인다 (실측)

`jobCustCd=101000`(개발 테스트 코드)으로 우리 실제 송장을 조회하면 전부 실패한다.

```
invNo=313633845254 (롯데 문서 예제)  → code:S  정상 조회
invNo=258131494106 (우리 실제 운송장) → code:E  거래처코드의 운송장번호에 대한 정보가 없습니다.
invNo=259998951133 (우리 실제 원송장) → code:E  거래처코드의 운송장번호에 대한 정보가 없습니다.
```

**우리 화물을 조회하려면 우리 `jobCustCd` + 운영 환경 키가 있어야 한다.**
개발 환경에서 할 수 있는 검증은 여기까지다.

```
총 12자리

[ 앞 11자리 = 일련번호 ][ 1자리 = 체크digit ]

체크digit = (앞 11자리를 하나의 정수로 본 값) mod 7      ← 0~6 사이

예) 3030-4040-5054
    앞 11자리 : 30304040505
    마지막자리 : 4   (30304040505 mod 7 = 4)
```

- 운송장번호 대역은 **영업담당자를 통해 받는다.** 번호가 부족해지기 전에 신규 대역을 요청해야 한다.
- 문서상 **앞자리(첫 숫자)에 대한 제약은 없다.** 대역에 따라 달라진다.
  (롯데 예제는 `3`으로 시작, 우리 현장 라벨은 `2`로 시작)

### 검증 결과 (2026-08-31, 실제 라벨 16건)

| 대상 | 정식 규칙 (11자리 정수 mod 7) | 자릿수 합 mod 7 |
|---|---|---|
| 운송장 9건 | **9/9 통과** | 1/9 |
| 원송장 7건 | 5/7 통과 (2건은 OCR 오독 의심) | 2/7 |
| 안심번호 6건 (송장 아님) | 0/6 — 전부 정상 배제 | 0/6 |

> **`csBarcodeParse.gs` 의 `csValidateLotteChecksum_` 는 "자릿수 합 mod 7"로 잘못 구현돼 있다.**
> 그 때문에 `csLogistics.gs` 에 "실제 라벨 8건이 전부 실패해서 체크섬은 신뢰 조건에서 뺀다"는
> 주석이 달렸는데, 규칙이 안 맞는 게 아니라 구현이 틀린 것이다. 정정하면 9/9 통과한다.

```js
/** 롯데 12자리 체크섬 — 앞 11자리 정수 mod 7 == 12번째 자리 */
function csValidateLotteChecksum_(inv12) {
  var s = String(inv12 || "").replace(/[^0-9]/g, "");
  if (!/^\d{12}$/.test(s)) return false;
  var m = 0;                       // 11자리는 2^53 안이지만 자릿수 순회가 안전하다
  for (var i = 0; i < 11; i++) m = (m * 10 + (s.charCodeAt(i) - 48)) % 7;
  return m === (s.charCodeAt(11) - 48);
}
```

## 8. 우리 CS 웹앱 적용 판단

### 지금 상태

| 위치 | 현재 |
|---|---|
| `home.html` `trackingUrl()` | 택배사별 **조회 링크만** 생성. CS가 외부 사이트로 나가 눈으로 읽는다 |
| `csLogistics.gs` `csLogisticsMatch()` | 파손 송장을 확정/후보/미상 3단계로 **추정** 매칭 |
| `csBarcodeParse.gs` | 롯데 체크섬 구현이 틀려서 신뢰 신호로 못 쓰고 있다 |
| `csReturnIntake.gs` | 스캔해야 「입고검수」로 전환 |
| `csOrderSearch.gs` `사방넷_송장대량등록` | 출고 송장은 사방넷 경유 (`002` = 롯데) |

### 적용 우선순위

**1순위 — 체크섬 정정 (API 불필요, 즉시 가능)**
6장의 정정 코드를 반영하면 실측 9/9 통과. `csLogistics.gs` 의 `tier` 판정에서
`checksumOk` 를 다시 신뢰 조건으로 쓸 수 있어 `sure` 자동 처리 비율이 오른다.
동시에 `/^2\d{11}$/` 의 "2로 시작" 제약은 대역이 바뀌면 깨진다 — 채번규칙에는 그런 제약이 없다.
체크섬이 정상 작동하면 앞자리 제약 없이도 안심번호를 배제할 수 있다.

**2순위 — 표준 화물추적 (`custmer-view-tracking`)** ⛔ **화물추적 연계 등록 대기 — 착수 불가**
링크를 넘겨주는 대신 앱 안에서 상태·이력을 보여준다. 롯데 물량만 커버하고
나머지 택배사는 기존 링크 유지. `ordNo` 로도 조회되므로 송장이 아직 없는 건도 물린다.
⛔ **선결 조건: 화물추적 연계 등록.** 우리 거래처코드 `348782` 로는 개발 환경에서도
`영업담당자에게 문의하여 화물추적 연계 등록을 해주시기 바랍니다` 로 막힌다 (2-1장 참조).
영업담당자에게 등록을 요청해 풀리기 전까지는 **코드를 붙여도 검증할 수 없다.**

**3순위 — 반품 회수 접수 (`apiSndOut` + `ustRtgSctCd=02`)**
CS가 상담 중 회수 예약 → 응답 `invNo` 를 반품대장에 즉시 기록.
`orglInvNo` 없이도 접수되므로 원송장을 못 찾는 건도 처리된다.
이게 되면 `csLogistics` 의 추정 매칭은 **대조 확인용**으로 격하된다 — 우리가 발급한 번호이므로.

**보류 — 자체 운송장 출력 / 출고 주문접수**
출고 송장은 사방넷이 SSOT다. 지금 구조를 흔든다. B2B API도 우리 업무와 무관.
