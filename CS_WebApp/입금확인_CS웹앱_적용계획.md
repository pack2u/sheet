# 은행 입금 자동확인 — CS웹앱 적용계획

> 작성 2026-09-28
> 은행 입금 문자 → 자동 기록 → 이카운트 주문서 매칭 → CS웹앱 카드·구글챗 알림 → 확인 버튼 한 번으로 이카운트 입금 전표.
> 기존 `FileStore`(수신 전용 GAS)·`csHandoffBoard`(보드)·`_partnerChatNotify`(구글챗)·`ecount.gs`(이카운트 프록시) 관례를 그대로 따른다.

---

## 0. 배경 — 지금 무엇이 불편한가

1. **입금 확인을 하루 최소 3번** 한다. 매번 은행 화면·엑셀을 봐야 한다.
2. **이카운트 입금 처리가 두세 번 눌리면 그대로 두세 번 들어간다.** 채권이 틀어지고, 월말 정산 대조(`D:\이카운트\정산비교시트_*`)에서 뒤늦게 발견된다.
3. **금액이 모자라거나 남는 입금**이 종종 있다. 지금은 사람이 주문서와 눈으로 맞춘다.

목표는 **사람이 "처음 보는 입금자"와 "금액이 안 맞는 건"만 보게** 하는 것이다.

## 1. ★ 먼저 알아둘 제약 3가지 (코드 확인 결과)

### 1-1. 문자 수신은 CS웹앱 본체에 못 붙인다

CS웹앱은 `executeAs: USER_ACCESSING` + 허용 계정 검사(`csAccessControl.gs`)다.
폰 자동화 앱(MacroDroid)은 **구글 로그인을 못 하므로** CS웹앱 주소로 보내면 로그인 화면에 막힌다.

→ **`FileStore` 와 같은 방식의 수신 전용 GAS 프로젝트 `DepositInbox` 를 따로 둔다.**
`executeAs: USER_DEPLOYING` + `access: ANYONE` + **본문 토큰 검사**. FileStore `doPost` 구조를 그대로 베낀다.

### 1-2. 이카운트 오픈API에 "주문서 조회"가 없다

API 목록(2026-09-28 확인): 영업관리는 **견적서입력·주문서입력·판매입력**뿐. 조회는 구매 쪽 `발주서조회` 만 있다.

→ 주문서는 **이카운트 주문서현황 엑셀을 CS웹앱에 붙여넣기/올리기**로 가져온다(하루 1~3회).
주문번호로 중복을 거르므로 같은 파일을 여러 번 올려도 된다.

### 1-3. 입금 전표는 "일반전표" API로 넣는다 — ★사전테스트 필수

입금보고서 전용 API는 없다. 대신 **회계API > 일반전표** 로 아래처럼 넣으면 채권이 줄어야 한다.

```
차변  보통예금     500,000
대변  외상매출금   500,000   (거래처: 태양)
```

**거래처원장에 입금으로 잡히는지**, 계정코드가 맞는지 이카운트 **「API 직접실행(사전테스트)」**에서 1건 넣어 보고 확인한 뒤에 4단계를 연다.
이카운트 호출은 기존처럼 **고정 IP 프록시(`ecount-proxy`, 34.64.87.69)** 를 거친다(`ecount.gs` `_ecountFetchViaProxy_`).

## 2. 전체 구조

```
[은행 입금·출금 문자]
   └ 안드로이드 폰 (MacroDroid: 은행 번호만 거름)
        └ HTTPS POST {token, from, body, receivedAt}
             └ [DepositInbox GAS]  ← 수신 전용, 배포자 권한
                  ├ ① 문자 해석 (은행별 패턴)
                  ├ ② 고유번호 → 중복이면 무시
                  ├ ③ 입금대장 시트에 기록
                  ├ ④ 주문서 매칭 (일치/부족/초과/후보/미확인)
                  └ ⑤ 구글챗 「입금알림」 방으로 푸시

[CS웹앱 · 입금 탭]  ← 허용된 사람만
   ├ 입금 카드 목록 (pulse 로 자동 새로고침)
   ├ 주문서 엑셀 올리기
   ├ 후보 선택·별칭 지정·메모
   └ [이카운트 반영] 버튼 → DepositInbox → ecount-proxy → 일반전표
```

**CS웹앱은 입금 데이터를 직접 열지 않는다.** CS웹앱 → `UrlFetchApp` → DepositInbox(토큰)로 읽고 쓴다.
그래서 입금대장 시트와 이카운트 키는 **배포자 계정에만** 있고, CS 직원 계정에 시트 공유가 필요 없다.

## 5. 중복 방지 — 이번 작업의 핵심

사용자 불만 1순위가 "두세 번 눌리면 두세 번 들어간다"다. 세 겹으로 막는다.

| 겹 | 막는 것 | 방법 |
|---|---|---|
| **수신** | 같은 문자가 두 번 옴, 폰 앱 재전송 | 고유번호가 이미 있으면 **기록 안 하고 `ok:true, dup:true`** |
| **버튼** | 반영 버튼 연타, 두 사람이 동시에 누름 | `LockService` + 상태가 `확인됨` 인 것만 통과 → 즉시 `반영중` 으로 바꾼 뒤 API 호출 |
| **API 결과 불명** | 타임아웃으로 들어갔는지 모름 | **자동 재시도 금지.** `확인필요` 로 세우고 사람이 이카운트에서 확인 후 전표번호를 적는다 |

전표번호가 적힌 줄은 **어떤 경로로도 다시 보내지 않는다.** 화면 버튼도 사라진다.

## 6. 매칭 규칙

후보는 **상태가 미입금·일부인 주문서**만.

1. **이름 정리**: `(주)` `주식회사` `㈜` 공백 괄호 제거 후 비교 + 별칭표.
2. **금액 비교**

| 이름 | 금액 | 결과 | 다음 |
|---|---|---|---|
| 맞음 | 맞음 (후보 1건) | ✅ 일치 | `확인됨` — 반영 버튼만 누르면 된다 |
| 맞음 | 여러 주문 합이 맞음 | ✅ 일치(합산) | 오래된 주문부터 조합, 조합이 2가지 이상이면 `후보` |
| 맞음 | 모자람 | 🔴 부족 | 입금누계에 더함, 주문은 `일부` |
| 맞음 | 남음 | 🟡 초과 | 차액 표시, 사람이 처리 방법 결정 |
| 다름 | 맞음 | 🟠 후보 | 같은 금액 주문을 보여주고 사람이 고름 → 별칭표에 저장 |
| 다름 | 다름 | ⚪ 미확인 | 사람이 거래처 지정 또는 `제외` |

**1단계 운영은 "일치"도 사람이 반영 버튼을 누른다.** 두 달 정도 써 보고 틀린 적이 없으면 일치 건만 자동 반영으로 바꾼다(설정 한 칸).

이카운트에 넣는 금액은 **항상 실제 입금액**이다. 부족분은 채권 잔액으로 자연히 남는다.
초과분 처리(선수금 계정으로 넣을지 등)는 **2단계 사전테스트 때 결정**.

## 7. 놓친 문자 잡기

폰은 꺼지거나 앱이 죽을 수 있다. 조용히 놓치는 게 가장 위험하다.

- **잔액 연속성**: `직전 거래후잔액 ± 이번 금액 = 이번 거래후잔액` 이 안 맞으면 **"사이에 빠진 문자 있음"** 경고. 그래서 **출금 문자도 받는다**(매칭에는 안 씀).
- **생존 신호**: MacroDroid가 30분마다 `ping`. 1시간 넘게 안 오면 구글챗 「📵 입금 폰 연결 끊김」.
- **해석 실패**: 패턴에 안 맞는 문자는 버리지 않고 `미해석` 카드로 띄운다(원문 보존).
- **월말 대조**: 은행 거래내역 엑셀을 올리면 대장과 대조해 빠진 건·중복 건을 뽑는다(`정산비교시트`와 같은 방식).

## 8. 알림

**구글챗 「입금알림」 방** (새로 만든다. 돈 정보라 CS 방과 분리, 회계 담당만 초대).

```
✅ 태양 500,000원 — 주문 2026/09/27-3 일치
🔴 콤콤 300,000원 — 주문 대비 20,000원 부족
🟠 김철수 88,000원 — 같은 금액 주문 2건, 선택 필요
⚪ 이영희 150,000원 — 매칭 주문 없음
📵 입금 폰 연결 끊김 (마지막 신호 14:02)
```

CS웹앱 입금 탭은 `csPulse` 지문에 입금대장을 더해 **새 입금이 오면 저절로 다시 그린다.**

## 9. 권한

- CS웹앱 **입장 권한**(기존 `CS_ALLOWED_EMAILS`)과 별도로 **입금 탭 권한** `CS_DEPOSIT_EMAILS` 를 둔다.
  권한 없는 계정에는 탭 자체를 안 보인다(서버에서도 한 번 더 검사).
- 폰 → DepositInbox 토큰, CS웹앱 → DepositInbox 토큰은 **따로** 둔다. 폰을 잃어버리면 폰 토큰만 바꾼다.
- MacroDroid는 **은행 발신번호만** 보낸다. 인증번호·개인 문자는 밖으로 안 나간다.

## 10. 단계

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| **0. 사전 준비** (사용자) | 아래 "받아야 할 것" 전부 | 체크리스트 완료 |
| **1. 수신·기록·알림** | DepositInbox, 문자 해석, 입금대장, 중복 방지, 잔액 연속성, 생존 신호, 구글챗 | 실제 입금 1건이 챗으로 오고, 같은 문자 재전송 시 1줄만 남음 |
| **2. CS웹앱 입금 탭** | 카드 목록, 자동 새로고침, 권한, 제외·메모 | 허용 계정만 보이고 새 입금이 저절로 뜸 |
| **3. 주문서 매칭** | 엑셀 올리기, 매칭 규칙, 별칭표, 후보 선택 | 지난 1주 입금으로 돌려서 사람 판정과 대조 |
| **4. 이카운트 반영** | 일반전표 API, 반영 버튼, 3겹 중복 방지 | 사전테스트 통과 + 버튼 연타해도 전표 1건 |
| **5. 운영 다듬기** | 월말 은행 엑셀 대조, 일치 건 자동 반영 전환 여부 | 한 달 운영 후 결정 |

1단계만 끝나도 **"입금 오면 폰으로 바로 안다"** 는 쓸 수 있다. 4단계 전까지 이카운트는 기존대로 사람이 넣는다.

CS웹앱을 고칠 때마다 `CS_BUILD_` 올리고 **재배포까지** 한다(push만 하면 팀은 옛 화면).

## 10-1. V2 이식 대비 (2026-09-28 추가)

> "이것도 V2를 염두해서 만들어줘"
> `_docs/2026-09-14_시트→V2_이식전략.md` 원칙 세 가지를 처음부터 따른다.

| 원칙 | 입금확인에서 |
|---|---|
| **1. 규칙은 한 곳에만** | 해석·고유번호·잔액 연속성은 `DepositInbox/dpParse.gs` **한 파일**(순수 함수 + `module.exports`). V2 는 세트분리 `tools/syncCore.mjs` 처럼 배포 직전에 복사본을 심어 **같은 함수**로 읽는다. 3단계 매칭 규칙도 이 파일(또는 같은 모양의 `dpMatch` 순수 파일)에 둔다 |
| **2. 그림자 운전** | `dpMirror.gs` 가 **문자 원문** + 시트 해석 결과(대조용) + `coreVersion` 을 `/api/deposits/ingest` 로 보낸다. V2 는 원문을 다시 읽어 `deposits` 에 upsert(고유번호)하고, 시트 결과와 다르면 그 줄만 보여 준다 |
| **3. 되돌릴 수 있게** | 스크립트 속성 `DEPOSIT_MIRROR` = `on`/`off`. 받는 곳이 아직 없어 **기본 꺼짐**. 끊겼던 기간은 `dpMirrorBackfill(일수)` 로 다시 민다 |

**전용 토큰** `DEPOSIT_INGEST_TOKEN` — 명세서 ingest 처럼 이 경로만 연다. 서비스 키를 GAS 에 두지 않는다.

### V2 쪽에 만들 것 (다음 작업)

| 파일 | 내용 |
|---|---|
| `sql/65_deposits.sql` | `deposits` (key PK · received_at · from · body · 해석 칸 · sheet_json · core_version · diff) + RLS(직원 중 입금 권한만) |
| `app/src/lib/deposit/core.js` | `dpParse.gs` 의 그림자 (손으로 고치지 않는다) |
| `tools/syncDepositCore.mjs` | `syncCore.mjs` 와 같은 방식, `_v2deploy.mjs` 가 배포 직전에 부른다 |
| `app/src/app/api/deposits/ingest/route.ts` | 토큰 확인 → 원문 재해석 → upsert → 시트 결과와 다르면 diff 기록 |

**컷오버 때는** 폰의 수신 주소만 V2 로 바꾸면 된다. 해석 규칙이 한 파일이라 V2 로 넘어가도 결과가 같다.
