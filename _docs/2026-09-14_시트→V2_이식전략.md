# 시트 → V2 이식 전략

2026-09-14 · 사장님 제안에 대한 판단과 기획

> "결국 시트시스템이 완벽해야 v2로 이식이 가능하고 검증이 가능하다는거지..."
> "시트의 구조 및 데이타를 V2에 이식을 먼저하고.. 시트에서 오류 수정시에
>  V2도 같이 수정되는 시스템이 되어야 할꺼 같아"
> "시트 시스템에서 검증 시스템까지 구현하려다보니 오가는 데이타가 커지는 문제도 있어"

---

## 1. 지금 막혀 있는 것 — 이름을 붙이면

```
시트가 자꾸 터진다  →  고치느라 시간을 다 쓴다  →  V2 이식을 못 한다
        ↑                                                    ↓
  시트를 못 놓는다  ←  V2를 검증 못 한다  ←  비교할 기준이 안 선다
```

**돌고 있습니다.** 그래서 「시트를 완벽하게 만든 다음 옮긴다」는 순서로는 영영 못 빠져나옵니다.
시트는 완벽해지지 않습니다 — 매일 새 주문이 들어오고 업체가 늘고 양식이 바뀝니다.

고리를 끊는 지점은 **「검증하려면 시트가 완벽해야 한다」** 는 전제입니다.
이 전제가 틀렸습니다. 뒤에서 다룹니다.

---

## 2. 사장님 안에 대한 판단

### ✅ 맞는 것 — 데이터를 먼저 옮긴다

**정확합니다.** 데이터가 먼저 V2에 있으면, V2는 실무를 하나도 안 건드리고
**옆에서 같은 계산을 해 볼 수 있습니다.** 업무 중단 없이 검증이 됩니다.
이게 뒤에 나올 「그림자 운전」의 전제입니다.

### ✅ 맞는 것 — 시트가 검증까지 하려니 오가는 데이터가 커진다

**정확한 관찰입니다.** 그리고 이건 저절로 풀립니다 —
검증을 V2로 빼면 시트는 «계산만» 하면 되므로 **저절로 얇아집니다.**
지금 시트가 무거운 이유의 상당 부분이 「제가 한 일이 맞나」를 시트 안에서
다시 확인하는 코드입니다.

### ⚠️ 위험한 것 — 「시트를 고치면 V2도 같이 고쳐지는 시스템」

**원하시는 결과는 맞는데, 「같이 고친다」는 방법이 함정입니다.**

이건 제가 지어낸 말이 아니라 **이 코드베이스가 이미 값을 치르고 배운 것**입니다.
`_partnerReturnsV2Mirror.gs` 머리말에 그대로 적혀 있습니다:

> 양쪽에 규칙이 있으면 한쪽이 늦게 고쳐지고, **늦은 쪽이 조용히 틀린다.**
> 실제로 그 일로 협력업체가 반품 접수를 못 했다.

그래서 그 미러는 이렇게 만들어졌습니다:

> **여기서는 아무것도 해석하지 않는다.** 탭 이름과 시트에 보이는 값 그대로 보낸다.
> 머리글이 몇 번째 줄인지, 어느 열이 무엇인지 — **판단은 전부 v2가 한다.**

**규칙이 두 곳에 있으면 반드시 갈라집니다.** 사람이 아무리 조심해도요.

---

## 3. 그런데 원하시는 그 시스템이 **이미 한 군데 있습니다**

**세트분리 V2 입니다.**

```
core.js  ── Apps Script 가 그대로 읽는다
         └─ Node 가 그대로 읽는다
```

계산 로직이 **한 파일**이고, 시트와 서버가 **같은 파일**을 씁니다.
그래서 `core.js` 를 고치면 **양쪽이 동시에 고쳐집니다.** 갈라질 수가 없습니다.

README 에 이렇게 적혀 있습니다:

> 계산 로직은 `core.js` **한 파일**에 있고 Apps Script와 Node가 그 파일을
> 그대로 공유한다. **시트와 CLI의 결과가 갈라질 수 없다.**

그리고 실측:

| | 같은 자료(09/12 판매현황 248행) |
|---|---|
| 시트에서 (Apps Script) | **69.1초** |
| Node 로 (같은 `core.js`) | **0.123초** |

**사장님이 원하신 「같이 고쳐지는 시스템」의 정답은 「같이 고치기」가 아니라
「한 파일을 같이 쓰기」입니다.** 그리고 그 모양이 이미 검증됐습니다.

### 그래서 전략의 핵심 한 줄

> **세트분리가 한 것을 다른 모듈로 넓힌다.**
> 규칙은 한 파일에, 시트는 그 파일을 부르기만, V2도 그 파일을 부르기만.

---

## 4. 원칙 셋

### 원칙 1 — 규칙은 한 곳에만

- 계산 규칙은 **공유 파일 하나**에 둔다 (`core.js` 처럼)
- 시트 쪽 코드는 **자료를 읽어 넘기고, 결과를 받아 쓰기만** 한다
- 해석·판단·검증을 시트 코드에 새로 넣지 않는다

### 원칙 2 — 그림자 운전으로 검증한다

- V2가 **같은 입력으로 같은 계산**을 한다
- 결과는 **DB에만 쓰고 아무 데도 안 내보낸다**
- 매일 시트 결과와 **자동 대조**해서 **다른 줄만** 리포트한다
- 실무는 그동안 **시트가 계속** 한다

**이것이 「시트가 완벽해야 검증할 수 있다」를 깨는 지점입니다.**
시트가 틀려도 됩니다 — 다르면 **둘 중 어느 쪽이 틀렸는지 사람이 보면 됩니다.**
오히려 그 대조가 **시트의 버그를 찾아 줍니다.** 검증과 안정화가 같이 갑니다.

### 원칙 3 — 되돌릴 수 있게 넘긴다

- 한 기능씩 넘긴다. 통째로 안 넘긴다
- 넘긴 뒤에도 **시트 코드를 지우지 않는다.** 스위치로 끈다
- 문제가 생기면 스위치만 되돌린다

> 선례가 있습니다 — `_PO_V2_SABANG_SUPPLEMENT_ = false`.
> 세트분리(뉴)를 아직 안 믿을 때 이 한 줄로 꺼 두었고, 믿게 되면 `true` 로 켭니다.

## 5. 단계

### 0단계 — 출혈 멈추기 (지금, 1~2주)

시트를 «좋게» 만드는 게 아니라 **매일 터지는 것만** 막습니다.

- [x] 사방넷 대량등록 — 합포장 동봉 누락, 마감 이후 누락
- [x] 대리공급 중복 발주 (같은 회차 겹친 줄)
- [x] 중복검사가 전용양식을 보게
- [x] 푸시 이어달리기
- [x] 송장원장 — 안 바뀐 파일 안 열기
- [ ] **트리거 자리 확보** ← 이게 남았습니다

> 트리거가 20개 한도에 꽉 차서 **네 모듈의 이어달리기가 몇 달째 한 번도 안 돌았습니다.**
> `_pt_onEditSpillGuard_` 는 2026-07-15부터 몸통이 `return;` 뿐인 빈 함수인데
> 트리거는 협력업체 파일마다 살아 있습니다. `partnerRemoveSpillGuards()` 로
> 지우면 자리가 빕니다. **시간표는 안 건드려도 됩니다.**

**0단계에서 새 기능을 만들지 않습니다.** 고장난 것만 고칩니다.

### 1단계 — 원천을 V2로 복제 (해석 없음)

시트가 **보이는 값 그대로** V2로 보냅니다. 판단은 V2가 합니다.

| 원천 | 지금 |
|---|---|
| 판매현황 | 이카운트 붙여넣기 |
| 대리공급_임시기록 (+보관) | 푸시가 씀 |
| 협력업체_발주허브 | 수집이 씀 |
| 전용양식 AX + 마감탭 | 업체가 송장을 적음 |
| 반품관리대장 | 이미 미러 있음 ✅ |

- **시트 코드가 늘지 않습니다.** 계산을 안 하니 오히려 줄어듭니다
- `/api/*/ingest` 패턴이 **이미 12개** 있습니다. 새로 설계할 게 없습니다
- 이 단계가 끝나면 V2는 **실무를 하나도 안 건드리고** 모든 자료를 갖습니다

### 2단계 — 그림자 운전 (검증)

V2가 같은 입력으로 계산하고 시트 결과와 자동 대조합니다.

```
판매현황 ──┬─→ 시트 세트분리 ──→ 출력 탭 ──→ 실무 (진짜)
           └─→ V2 세트분리  ──→ DB      ──→ 대조 리포트
```

매일 아침 이런 게 옵니다:
```
세트분리 대조 260914-1
  입력 248행 · 일치 246 · 다름 2
  ★ 0914-PH-a1b2  배송비  시트 3,600  /  V2 3,000   ← 봐야 함
  ★ 2162215846    경로    시트 대리발송 / V2 자사출고
```

- **다른 줄만** 옵니다. 같으면 조용합니다
- 틀린 쪽이 V2면 V2를 고칩니다. **시트면 시트 버그를 찾은 겁니다**
- 세트분리는 **오늘 당장** 시작할 수 있습니다 — `core.js` 가 이미 공유되고 0.123초입니다

**N일 연속 「다름 0」이 검증입니다.** 그때 비로소 그 기능을 넘깁니다.

### 3단계 — 화면부터 넘긴다 (쓰기는 아직 시트)

읽기 화면은 V2가 이미 낫습니다. 진실의 원천은 여전히 시트입니다.

- CS 주문검색 ← 통합조회(21:00)를 대체 → **트리거 한 자리 + 5분 예산 회수**
- 반품 현황 · 정산 — 이미 V2에 있음

### 4단계 — 한 기능씩 스위치

그림자 대조가 N일 연속 0건인 기능만, 스위치 한 줄로 넘깁니다.
시트 코드는 **지우지 않고 끕니다.**

## 6. 「데이터가 커서 시트가 터진다」 — 반은 맞습니다

**진짜 원인은 «양»이 아니라 «왕복 횟수»입니다.**

| | 한 번에 드는 값 |
|---|---|
| `openById()` 파일 열기 | **~1초** |
| `getRange().getValues()` | ~50~300ms |
| `SpreadsheetApp.flush()` | ~0.2~1초 |
| Postgres 인덱스 조회 (수천 행) | **~5~30ms** |

248행을 처리하는 데 GAS 69초 / Node 0.12초 — **같은 양, 같은 코드**입니다.
자료가 커서가 아니라 **자료에 닿는 값이 비싸서** 느립니다.

그래서 시트에서 효과가 큰 최적화는 이것들입니다:

1. **파일을 덜 연다** — 송장원장 48곳 → 10여 곳 (어제 적용)
2. **`flush()` 를 줄인다** — 마감이 업체당 4~5회. 48곳이면 200회 이상
3. **읽고 쓰는 횟수를 줄인다** — 한 줄씩 말고 한 번에

**양을 줄이는 것보다 왕복을 줄이는 게 효과가 큽니다.**

동시에 갈 수 있습니다 — **데드락을 여기서 끊습니다.**

## 붙임 — 하지 말아야 할 것

- ❌ 시트와 V2에 **같은 판단 규칙을 두 벌** 만들기 → 반드시 갈라집니다
- ❌ 시트를 «완벽하게» 만든 다음 옮기기 → 완벽해지지 않습니다
- ❌ 한꺼번에 넘기기 → 하루도 못 버팁니다
- ❌ 넘긴 시트 코드를 지우기 → 되돌릴 길이 없어집니다
- ❌ 시트에 **검증 코드를 더** 넣기 → 지금 무거운 이유가 그것입니다
