# 사방넷 API 1단계 — 송장전송 설계

> 작성 2026-10-09 · **미가입 상태. 개발가이드 미확보.**
> 이 문서는 «스펙을 모르는 채로» 쓴 것이다. 확정된 것과 가정을 반드시 갈라 읽을 것.

---

## 0. ★ 가장 중요한 것 — 부가서비스가 둘이다

```
우리 시스템 ──[API 서비스]──▶ 사방넷 등록 ──[자동화 서비스]──▶ 쇼핑몰
                월 5~50만원                     별도 과금 (금액 미확인)
```

**API 서비스만 가입하면 쇼핑몰 송신은 사람이 사방넷에서 누른다.**

근거 — 독립 3출처가 같은 말을 한다.

| 출처 | 원문 |
|---|---|
| 품고 | "자동화 서비스 미사용 시 사방넷에서 송장번호 송신 작업의 단계를 거쳐야 쇼핑몰에 송장번호가 전송" |
| FASSTO | "출고된 주문의 송장번호는 사방넷에 자동으로 등록됩니다. 이 송장번호를 쇼핑몰에 송신하는 작업은 직접 진행해 주세요" |
| 사방넷 연동 안내 | "사방넷에서 각 쇼핑몰로 송장번호가 자동으로 전송되기 위해서는 사방넷 내에서 '자동화 서비스' 이용이 필요합니다" |

→ **자동화 서비스 금액을 모르면 1단계 투자 판단이 성립하지 않는다.** 상담에서 반드시 같이 물을 것.

## 1. 확정 / 가정 구분표

지키는 규칙: **가정에는 코드를 쓰지 않는다.** 실측으로 확정된 뒤에 쓴다.

### 확정 (공개 출처 교차 확인)

| 항목 | 내용 |
|---|---|
| 송장 등록 | API로 사방넷에 등록 가능 (품고·FASSTO·메이크디·셀링콕 운영 중) |
| 인증 재료 | 샵ID(사방넷 마스터 로그인 ID) + API 인증키 |
| 인증키 위치 | 마이페이지 > 서비스 관리 > 연동키 관리 |
| 요금 | API 서비스 월 5만(싱글·레귤러·브론즈) / 10만(실버·골드) / 30만(스페셜1,2) / 40만(스페셜3,4) / 50만(플래티넘1,2) |
| 쇼핑몰 송신 | 자동화 서비스 별도 필요 (위 0장) |

### 가정 — 전부 실측으로 확인해야 한다

| # | 가정 | 틀리면 생기는 일 |
|---|---|---|
| A1 | 엔드포인트가 HTTP(S)로 직접 호출된다 | "XML 파일을 웹에 올려두고 URL만 알려주는" 방식이면 **호스팅에 파일 생성 단계가 추가**된다 (relay 호스팅 재사용 가능) |
| A2 | 요청/응답이 XML이다 | JSON이면 파서만 교체 — 어댑터 안이라 영향 작음 |
| A3 | 응답에 건별 성공/실패가 담긴다 | 전체 성공/실패만 오면 **"건별 결과 수신"이라는 1단계 이득이 사라진다** |
| A4 | IP 제한이 없다 | 있으면 relay 경유 (이미 있음, 추가비용 0) |
| A5 | 테스트 환경이 있다 | 없으면 **실주문으로 첫 호출**해야 한다 → 1건 전송부터 시작 |
| A6 | 한 번에 수백 건 전송 가능 | 상한이 낮으면 분할 전송 + 재시도 로직 필요 |
| A7 | 같은 주문번호 재전송이 멱등(덮어쓰기) | 아니면 중복 등록되거나 거부됨. **재시도 설계가 여기서 갈린다** |
| A8 | 택배사코드가 대량등록 엑셀과 같다 | 다르면 `_PEP_CARRIER_SABANG_CODE_` 매핑을 하나 더 둔다 |

**A3·A7이 1단계의 성패를 가른다.** 나머지는 어댑터 안에서 흡수된다.

7. **1회 전송 건수 상한**과 호출 빈도 제한이 있습니까?
8. 택배사 코드가 **송장대량등록 엑셀과 동일**합니까? (현재 사용: 001 CJ / 002 롯데 / 007 로젠 / 037 대신)

### 환경

9. **테스트(개발) 환경**이 있습니까? 없으면 실주문으로 시작해야 합니까?
10. **호출 IP 제한**이 있습니까? 있으면 등록 절차를 알려주세요. (고정 IP 보유: 222.122.39.14)

12. 개발 가이드가 `r.sabangnet.co.kr/RTL_API/` 에서 403으로 막혀 있습니다. 문서를 어떻게 받습니까?

### 주문·취소 (4·5·6번 과제용)

16. 쇼핑몰 취소가 발생하면 사방넷에 **자동으로 `취소 접수` 처리**됩니까, 사람이 눌러야 합니까?

### 상품·가격·옵션·상세 (1·2·3번 과제용 — 기대치를 낮게 잡고 확인한다)

22. 상품수정 API가 **가격 필드만 보내는 부분수정**을 받습니까, 상품 전체를 다시 전송해야 합니까?
    → 전체 재전송이면 「빠른 단가수정」이 성립하지 않고, 상품 전체를 우리가 SSOT로 보유해야 한다.
23. 부분수정이 안 되면, 일부 필드를 비워 보냈을 때 **기존 값이 유지됩니까, 지워집니까?**
24. **옵션(그룹상품)** 을 API로 수정할 수 있습니까? 스마트스토어 조합형/단독형, 쿠팡 아이템 단위처럼
    **몰마다 다른 옵션 구조**를 사방넷이 어디까지 흡수합니까?
25. **같은 상품에 쇼핑몰마다 다른 상세설명(HTML)** 을 보낼 수 있습니까?

    (즉시인지, 주기적인지 — 「빠른 수정」의 실제 반영 속도)
28. **쇼핑몰별로 다른 판매가**를 API로 보낼 수 있습니까? (같은 상품, 몰마다 다른 가격)
    → ①번 과제의 송출 단계. 화면에서는 되더라도 API로 되는지는 별개다.

    → 명목 수수료율로 계산하면 실제와 어긋난다. 실효수수료율을 역산하려면 이 데이터가 필요하다.
30. 몰별 **상세 이미지 규격**(권장폭·장수·용량 상한)과 **허용 HTML 태그** 제약을 사방넷이 안내해 줍니까?
    → 추측으로 만들면 업로드에서 반려된다. 확인된 값만 표에 넣는다.

### 4번 — 차단 지점과 시각

```
09:30/13:00/15:00 수집 ─┬─ ① 세트분리 전   → 보류(미발송) 탭. 가장 깨끗
10:30/15:40 임시기록 ───┼─ ② 발주대기      → 13:50 푸시가 되살리기 전 제거
13:50 대리공급 Push ────┼─ ③ 이후: 업체에 나감 → 업체 연락 필요
16:40/16:50 송장 ───────┴─ ④ 이후: 출고중지 요청 → 사실상 반송 전환
```

기존 훅 둘:

| 경로 | 장치 | 근거 |
|---|---|---|
| 자사출고 | **`보류(미발송)` 탭** + `보류사유`·`조치` | [세트분리V2/core.js](../세트분리V2/core.js) `SS_HOLD_HEADER`. 라우팅 안 된 전 행이 사유와 함께 모임 → **취소를 새 보류사유로 추가** |
| 대리공급 | **`발주대기`** | [_partnerExclusivePush.gs](../_partnerExclusivePush.gs) `_PEP_TEMP_WAIT_`. "아직 안 나갔다" 상태 |

`분해행 = 모든 탭 행수 합계`(`ROW_LOSS`) 검증이 있어 **취소로 빼낸 건이 조용히 사라지지 않는다.**

→ ①②에 닿으려면 취소 폴링이 **10~15분 주기**여야 한다 (Q17). 사방넷 측 `취소 접수`가 수동이면(Q16) 실효성이 그만큼 깎인다.

### 구조적 판단

```
주문 · 송장 · 재고 · 취소 · 클레임  →  사방넷이 강한 영역   (4·5·6)
상품 · 가격 · 옵션 · 상세페이지      →  사방넷이 약할 수 있는 영역 (1·2·3)
```

**가입 근거는 4·5·6(+송장·주문수집·재고)으로 잡는다.**
1·2·3을 근거로 삼으면 "막상 연결하니 안 되네"가 날 확률이 가장 높다.
1·2·3은 Q22~Q27 답을 보고, 안 되면 **몰 공식 API 직접 연동**(스마트스토어 커머스API · 쿠팡 WING API)을 별도 과제로 분리한다.

### ① 몰별 판매가 — 설계

기존 [마진계산기/marginCalculator.gs](../마진계산기/marginCalculator.gs) 를 확장한다.

```
기준원가 = (N×V) + Q + S                           ← 기존 그대로
                                                      N 박스입수량 · V 상품원가
                                                      Q 박스배송비 · S 포장비

몰별 판매가 = ROUNDUP(
    (기준원가 + 몰별고정비) /
    (1 − 목표마진 − 몰수수료율 − 쿠폰·프로모션 부담률),
    올림단위 )
```

신규 「쇼핑몰정책」 탭:

| 몰 | 수수료율 | 배송비정책 | 쿠폰부담률 | 몰별고정비 | 올림단위 | 추가할인 |
|---|---|---|---|---|---|---|

- "특정 몰만 얼마 내리자" = `추가할인` 한 칸
- **반영 전 미리보기 + 사람 확인**은 기존 마진계산기·[_partnerPriceRaise.gs](../_partnerPriceRaise.gs) 손버릇을 따른다
  (가격을 바로 덮어쓰지 않는다 — 틀리면 발주·명세서·정산이 전부 그 값을 믿는다)

**관건은 수수료율 출처다.** 명목률로 계산하면 실제와 어긋난다 (프로모션 분담·쿠폰·정산차감).

```
실효수수료율 = (판매액 − 실입금액) / 판매액      ← 몰별·월별
```

**현재 시스템에 쇼핑몰 정산 데이터가 없다** (몰 정산·수수료 모듈 부재 확인).
[csStatement.gs](../CS_WebApp/csStatement.gs) 는 협력업체 매입 명세서이고 몰 판매 정산이 아니다.

| 갈래 | 방식 | 정확도 | 사방넷 필요 |
|---|---|---|---|
| a | 몰별 명목 수수료율 수동 입력 | 대략 | ❌ **지금 가능** |
| b | 정산 데이터로 실효율 역산 | 정확 | Q29 확인 필요 |

→ **a 로 시작해 b 로 간다.** 계산은 사방넷 없이 지금 만들 수 있고, 사방넷은 **몰에 밀어넣는 마지막 단계**에만 필요하다 (Q28).

### ② 상세페이지 생성 파이프라인 — 설계

```
[사진 폴더] ──스크립트(결정적)──▶ 몰별 규격 이미지
                                        │
[텍스트 파일] ──Claude(판단)──▶ 카피 · 구성 · HTML
```

|---|---|---|---|---|

## 2-D. 무인화 원칙 · 몰 14개 전제 (2026-10-09 사장님 확인)

### 운영 몰

**스마트스토어 · 쿠팡 · 11번가 · 지마켓 + 추가 10개 이상 = 14개 이상**

### 목표는 완전 무인 — 엑셀은 중간 산출물일 뿐이다

```
사람 승인 방식:  생성 → [사람이 봄] → 전송        ← 사람이 병목
무인 방식:      생성 → [코드가 규칙 검사] → 전송
                             └ 위반만 → 보류 + 알림
```

**이 프로젝트가 이미 쓰는 방식이다.** 세트분리는 무인으로 돌고 `보류(미발송)` 만 사람이 본다.
`분해행 = 탭 합계`(`ROW_LOSS`) 가 누락을 막는다. 가격·상세도 같은 모양으로 만든다.

### 송장 → 쇼핑몰 송신: A 확정 (B 기각)

| | 방법 | 몰 14개에서의 평가 |
|---|---|---|
| **A** | 사방넷 **자동화 서비스** 가입 | **채택.** 14개를 하나로 묶는 것이 사방넷의 존재 이유 |
| B | 몰 공식 API 직접 | **기각.** 몰별 API 성숙도 편차가 크고(소형몰 상당수는 API 부재 가능), 14개 신청·인증·스펙·유지보수가 비현실적. API 없는 몰은 결국 사방넷을 거치므로 **두 체계를 동시 운영**하게 된다 |
| C | RPA 로 송신 버튼 클릭 | 기각. 약관·화면변경 리스크 |

→ 자동화 서비스 **과금 단위 확인 필수**: 정액 / **몰당** / 건당. 14개면 몰당 과금 시 금액이 크게 달라진다.

### ★ 우선순위 재조정 — 재고송신이 1순위

몰이 14개면 **과판매 위험이 14배**다. 재고 3개가 14개 몰에 각각 "3개 있음"으로 떠 있다.

> 트리거 주석(사장님): *"요즘 품절상품이 많아 주문시 상태값이 안보여 취소하는 일들이 많이 생겨"*

몰 4개면 사람이 눈치로 버티지만 **14개면 구조적으로 불가능**하다.

| 순위 | 항목 | 이유 |
|---|---|---|
| **1** | **재고송신 + 세트 가용재고(BOM 역산)** | 과판매·취소를 원천 차단. 14배 리스크 |
| 2 | 송장전송 + 자동화 서비스 | 14개 몰 송신이 한 번에. 무인 달성 |
| 3 | 주문수집 | 판매현황 수작업 3회 제거 + 몰 코드 확보 |
| 4 | 몰별 판매가 | 14 × 상품수 = 사람이 못 하는 규모 |
| 5 | 문의·클레임 | 14개 몰에 흩어진 CS 통합 |
| 6 | 상세페이지 | 상위 몰만 (아래) |

**1·2 순서를 바꾼 이유**: 송장은 「늦게 나가는」 문제, 과판매는 「이미 틀린」 문제다. 후자가 먼저다.

세트 가용재고:
```
세트 판매가능수량 = min( 구성품재고 ÷ 소요량 )
```
세트분리V2 가 `수량 = 주문수량 × 소요량` 으로 이미 BOM 을 쓴다. 역산 능력이 있고, 그 값이 몰로 가지 않는 것뿐이다.

### 가격 — 무인 전송 + 가드레일 (사람 승인 대체)

```
기준원가 변경 감지 → 몰별 가격 계산 → [가드레일] → 자동 전송
                                        └ 위반 → 「가격보류」 탭 + 알림
```

| 검사 | 막는 사고 |
|---|---|
| 변동률 상한 (예 ±15% 초과) | 원가 입력 오류가 가격에 번지는 것 |
| **원가 역전** (판매가 ≤ 기준원가) | 팔면 손해인 가격 송출 |
| 하한가 (몰별 최저 허용가) | 0원·비정상 저가 |
| 전일 대비 급변 **건수** 상한 | 전건이 한꺼번에 틀어지는 사고 |
| 세트·소분 줄 제외 | [_partnerPriceRaise.gs](../_partnerPriceRaise.gs) 가 이미 지키는 원칙 |

정상 범위는 사람 없이 나가고, 이상한 것만 걸린다.

### 상세페이지 — 무인 생성 + 규격 검증. **단 14개 전부는 하지 않는다**

```
상위 몰 (스마트스토어·쿠팡 등 매출 대부분)  →  몰별 최적화 버전
나머지 몰                                    →  공통 기본형 1개
```

생성은 자동이라 14개를 만들 수는 있다. 그러나 **검증·유지보수가 사람 일로 남는다** —
상품 1개 수정 → 14개 재생성 → 14개 배포 → 14곳 검증. 몰 규격 변경 시 14곳 대응.
매출 파레토를 따라 **상위 2~4개만 최적화해도 효과의 대부분**을 가져간다. 효과 확인 후 하나씩 늘린다.

규격 검사 (전부 자동):
- 몰별 이미지 폭·장수·용량 상한 · 금지 태그(script/iframe 등) · 필수 섹션 존재 · 이미지 깨짐/누락 · 과장광고 금지 문구

> 가격이 틀리면 즉시 돈이 틀리지만, 상세가 어색하면 **서서히** 매출에 영향을 준다 — 즉시 드러나지 않는다.
> 초기 2주는 생성물을 보류 탭에 쌓아 눈으로 본 뒤 자동 업로드를 켜는 편이 안전하다. 이후 완전 무인.

`ss_사방넷엑셀저장`([세트분리V2/gasMain.js:52](../세트분리V2/gasMain.js))이 만드는 행은 이미 두 시험이 지키고 있다 —

**② 스펙 불확실성을 한 파일에 가둔다.**
A1~A8이 어떻게 판명되든 바뀌는 곳은 `sabangAdapter.gs` 하나다.
`sabangSend.gs`(재시도·로그·결과 반영)와 세트분리 출력부는 손대지 않는다.

**③ relay 는 로젠 패턴을 그대로 복제한다.**
[_logen_relay/relay.php](../_logen_relay/relay.php)가 이미 검증한 것 —
화이트리스트로 API 이름 제한 · 비밀은 config 분리(.gitignore) · GET으로 열면 판 번호만 알려줌 ·

**같은 규칙을 그대로 따른다. 새로 발명하지 않는다.**

> GAS는 발신 IP가 구글 대역에서 유동 배정되어 IP 제한 API를 못 부른다 (로젠에서 실측 확인:
> 미등록 IP는 401이 아니라 **TCP 연결 자체가 드롭**). A4가 "제한 있음"으로 나오면 relay 가 유일한 길이다.

## 4. 작업 순서 — 실측이 코드보다 앞선다

### 0단계 · 실측 (코드 아님)  ← 가입 직후 첫 작업

목표: **아무것도 바꾸지 않고 응답만 받아 본다.**

1. `sabang.php` 를 relay 호스팅에 올린다 (화이트리스트에 송장 API 이름 하나만)
2. GET으로 열어 판 번호가 보이는지 확인 (0바이트 업로드 사고 방지 — 로젠에서 겪은 것)
3. **실주문이 아닌 값**으로 1건 호출 → 응답 원문을 그대로 저장
4. 이어서 **실주문 1건**으로 호출 → 사방넷 화면에서 등록됐는지 눈으로 확인

### 1단계 · 실측 메모 작성

`_docs/사방넷_API_규격.md` 를 만들고 **맨 앞에 「★ 실측 메모 — 문서와 다른 것들」** 을 둔다.
로젠 문서와 같은 형식이다. A1~A8 각각에 실제 관측값을 적는다.

이 문서가 없으면 다음 사람이 가이드만 믿고 또 같은 데서 넘어진다.

### 2단계 · 어댑터 + 드라이런

`sabangAdapter.gs` 작성. **단, 전송은 하지 않는다.**
`drySend()` 가 "보낼 요청 본문"을 로그로만 남긴다. 기존 엑셀과 내용이 같은지 대조한다.

### 3단계 · 병행 운영 (최소 2주)

```
매 회차:  엑셀 생성(기존, 사람이 업로드)  +  API 전송(신규)
          → 두 결과를 대조. 어긋나면 API 쪽을 고친다.
```

이 기간에는 **엑셀이 정답**이다. API는 검증 대상이다.

### 4단계 · 전환

대조가 2주 연속 일치하면 엑셀 업로드를 멈춘다.
**엑셀 생성 기능은 지우지 않는다** — 사방넷 장애 시 되돌아갈 길이다.

---

## 5. 수용 시험 — 1단계 성공의 정의 (미리 못 박는다)

전환(4단계) 조건. 하나라도 불충족이면 전환하지 않는다.

| # | 조건 | 왜 |
|---|---|---|
| S1 | 한 회차 전량이 1회 호출로 등록되고, 사방넷 화면 건수가 엑셀 업로드 때와 **같다** | 누락 없음 |
| S2 | 실패 건을 **건별로** 식별할 수 있다 | A3. 불가하면 1단계 핵심 이득이 없다 → 전환 보류 |
| S3 | 같은 회차를 두 번 전송해도 사방넷에 **중복 등록되지 않는다** | A7. 재시도 안전성 |
| S4 | 우리가 만든 UID(`PH-`, `ds-`)가 **거부되거나 애초에 안 나간다** | [_sabanguid_test.js](../_sabanguid_test.js)가 막는 그 사고 |
| S5 | 합포장 — **여러 주문번호 → 같은 송장**이 각각 등록된다 | [_sabangone_test.js](../_sabangone_test.js) 주석의 사장님 확인사항. 막으면 안 되는 쪽 |
| S6 | 한 주문번호에 송장 여럿을 보내면 **대표 1개만** 들어간다 | 같은 시험. 막아야 하는 쪽 |
| S7 | 전송 실패가 **조용히 넘어가지 않는다** — 로그 + 화면 알림 | 프로젝트 공통 원칙 |
| S8 | 2주 병행에서 엑셀 ↔ API 결과가 **전건 일치** | |

**S2가 불충족이면 1단계를 중단하고 2단계(주문수집)로 넘어가는 것이 낫다.**
건별 결과를 못 받으면 "업로드 클릭 한 번"이 "API 호출 한 번"으로 바뀌는 것뿐이고, 월 요금을 정당화하지 못한다.

## 6. 손실 한계

| 시점 | 실패하면 | 손실 |
|---|---|---|
| 0단계 (실측) | 응답이 예상과 전혀 다름 | **API 서비스 1개월분.** 해지. 코드 0줄 |
| 2단계 (드라이런) | 요청 본문을 못 만듦 | 1개월분 + 어댑터 작업시간. 운영 영향 **없음** |
| 3단계 (병행) | 대조 불일치 | 운영 영향 **없음** (엑셀이 정답) |
| 4단계 (전환) | 사방넷 장애 | 엑셀 경로로 즉시 복귀 |

**운영 사고가 날 수 있는 구간이 없다.** 병행 기간 동안 기존 경로가 계속 정답이고, 전환 후에도 엑셀 생성이 살아 있다.
