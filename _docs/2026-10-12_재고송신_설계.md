## 0. 0단계 결과 — 지금 무슨 일이 벌어지고 있나

### ★ 품절 60건 가운데 31건이 지금 14개 몰에서 팔리고 있다 ★

| 우리 상태 | 건수 | 사방넷에서 지금 |
|---|---:|---|
| **품절** | 60 | **`IN_SUPPLY` 31** · 없는 코드 27 · `UNUSED` 2 |
| 단종품·소싱중·상세제작중 | 142 | **`IN_SUPPLY` 40** · 없는 코드 92 · `UNUSED` 7 · `PAUSE` 3 |

**71건이 「팔면 안 되는데 팔리고 있다」.** 이것이 재고송신의 즉시 효과다.
(「없는 코드」는 사방넷에 안 올린 품목이다 — 몰에서 안 파니 문제가 아니다.)

### 미러는 살아 있다

| | |
|---|---|
| `products` | **3,511줄** · 일곱 낱말의 합이 전체와 같다 → check 밖의 값 없음 |
| 가장 최근 `updated_at` | **2026-10-12 03:04** · 오늘 갱신된 줄 **3,370** |
| `sabang_status_sent` 칸 | **없다** (8장에서 만든다) |

분포(오늘): 판매중 3,121 · 품절임박 136 · 단종품 80 · 품절 60 · 소싱중 58 ·
판매중(재고까지만) 52 · 상세제작중 4.

> **「특판/할인」은 0건**이다 (6장 ★). 일곱 합 3,511 = 전체이므로
> 지금 거부되고 있는 줄은 없다.

### 사방넷은 코드 하나씩만 받는다

목록·페이지·상태필터를 다 찔러 봤다 — **전부 400**이다.

```
GET /v3/sb/product            → 「품번코드 또는 자체상품코드 필수 입력값입니다」
?page=1&size=5                → BAD_REQUEST
?pageNo=1&pageSize=5          → BAD_REQUEST
?customProductCode=A,B        → 「유효하지 않은 자체상품코드」 (쉼표를 코드로 읽는다)
?productSupplyStatusCode=…    → BAD_REQUEST
```

전수 조사는 **3,511 호출 · TPS 10 을 8/초로 눌러 약 7분**이다.
운영 중 대조에는 못 쓴다 — **우리 쪽 상태 변화를 기준으로** 보내야 하는 까닭이다.

| 판매중 | 2,344 | | 304 | 14 | 459 |
| 품절임박 | 97 | | 1 | 1 | 37 |

### ★★ `OUT_OF_STOCK` 이 «한 건도» 없다 ★★

3,511건 전부를 봤는데 `OUT_OF_STOCK` 이 0건이다.
**이 계정은 사방넷에서 품절 관리를 해 본 적이 없다.** 두 가지가 따라온다.

| | |
|---|---|
| **좋은 쪽** | 올릴 대상이 **0건**이다. 올리기는 「**우리가** 내린 것을 되올리는」 길로만 존재한다 → 사방넷에 되묻지 않고 `sabang_status_sent` 만으로 판단할 수 있다. 사람이 `OUT_OF_STOCK` 을 쓰지 않으니 우리 기억과 어긋날 일이 없다 |
| **★ 위험한 쪽** | **아무도 써 본 적 없는 상태값을 쓰려 한다.** `results[].status=true` 는 「사방넷이 받았다」는 뜻일 뿐, **쿠팡·스마트스토어 화면이 실제로 품절로 바뀌는지는 별개다.** 3단계에서 **몰 화면을 눈으로 확인**해야 한다 ([[verifiable-samples-beat-new-numbers]]) |

> 「없는 코드」 624건 중 505건은 우리가 「판다」고 하는 품목이다 —
> **몰에 안 올린 것**이다(자사 전용·업체 전용). 결함이 아니다.
>
> 「판매중인데 사방넷은 `UNUSED`」 304건도 결함이 아니다 — 사람이 몰에서
> 내려둔 것이다. **우리가 올리지 않는다** (3장).

## 1. 설계가 세 번 줄었다

| 처음 생각 | 실측 뒤 |

| 옵션(단품) 레벨에 `stockQuantity` 밀기 | **필요 없다.** `stockUseYn="N"` 이라 재고관리를 안 쓴다 |

**남은 일은 「상태값 하나를 옮기는 것」뿐이다.**

## 2. 구조 — 상품정보시트를 «한 번도 더» 읽지 않는다

```
상품정보시트  ──(이미 있는 미러)──▶  v2  products.status  ┐
 (이카운트 배치 직후)                                     ├─▶ 판정 한 곳
   _productsV2Mirror.gs                                  │   (v2 함수 하나)
   → /api/products/ingest                                │        │
                                                         │        ▼
팩투유 품절상품 시트 ─(시트거울 30분)─▶  v2  stockouts   ┘   sabang.php
                                                           @222.122.39.14
                                                                  ▼
                                                  POST /v3/sb/product/upsert
```

### 왜 v2 에서 도나

| | |
|---|---|
| **시트 부하 0** | `products`·`stockouts` 둘 다 이미 채워져 있다. 시트를 다시 안 읽는다 |
| **GAS 트리거 0** | 트리거는 18개까지인데 거의 찼다 ([[gas-trigger-slots-reserve-two]]) |
| **방향이 맞다** | [[full-migration-to-v2]] — 새 일은 v2 에 둔다 |
| **중계기 재사용** | v2(Vercel)도 발신 IP 가 유동이라 중계기가 필요하다 — **이미 있다** |

### 미러가 보내는 칸 — 이름이 맞는지 확인했다

`_productsV2Mirror.gs:188` 이 보내는 것과 `/api/products/ingest` 가 받는 것이 같다:

```
ecount_code · item_name · status ← 이것 · stock_qty · supplier_name · warehouse
```

> **미러는 「이카운트 배치 직후에만」 돈다** — 그래야 `updated_at` 이
> 「이카운트에서 받아온 시각」과 같은 뜻이 된다. 하루 한 번이다.
>
> ★ 재고송신은 그 미러에 매달지 않는다 ★ **30분마다** 돌아
> 품절상품 시트에 적힌 것을 바로 걸어 준다 (3장 「빠른 길과 넓은 길」).
> `products` 가 하루 한 번 갱신돼도 바뀐 줄만 보내므로 헛걸음이 없다.

### v2 에 낼 자리 — 이미 있는 본을 따른다

```
app/src/app/api/cron/sabang-stock/route.ts     ← 새로
app/src/lib/sabang-stock.ts                    ← 판정은 여기 한 벌만
sql/NNN_sabang_stock.sql                       ← 칸 추가 + cron.schedule
```

`sheet-mirror` · `daily-archive-pull` · `shadow` 가 전부 이 모양이다.

## 3. ★ 내리기는 넓게, 올리기는 좁게 ★

0단계에서 「손대지 않음」을 다시 봤다. **그 논리는 올릴 때만 맞다.**
단종품 40건이 사방넷에서 팔리고 있는데 「사람이 정한 것이니 손대지 않는다」고
비켜 가면, 팔면 안 되는 물건을 그대로 둔 것이다.

### 내릴 때 — 어느 한쪽이라도 「팔면 안 된다」면 내린다

| 입력 | 내리는 값 |
|---|---|
| `products.status` 가 **품절 · 단종품** | `OUT_OF_STOCK` |
| `stockouts` 에 **kind=품절** 로 있다 | `OUT_OF_STOCK` |

> **소싱중·상세제작중은 5단계 뒤에 넣는다.** 지금 내려 버리면 물건이 들어와도
> 올리는 길이 아직 없어서 **못 판다.** 10장 순서가 그래서 그 모양이다.

### 올릴 때 — 모두가 「팔아도 된다」고 해야 올린다

| 조건 | |
|---|---|
| `products.status` 가 판매중 · 품절임박 · 판매중(재고까지만) | **그리고** |
| `stockouts` 에 kind=품절 로 **없다** | **그리고** |
| 사방넷 현재 상태가 **`OUT_OF_STOCK`** | → `IN_SUPPLY` |

### 사방넷 쪽에서 손대지 않는 상태

| | |
|---|---|
| `WAITING` · `PAUSE` · `UNUSED` · `DELETE` · `NO_DATA` | **손대지 않는다** |
| `IN_SUPPLY` ↔ `OUT_OF_STOCK` | **이 둘 사이만 오간다** |

> 0단계에서 `UNUSED` 9건 · `PAUSE` 3건을 봤다.
> `UNUSED` 는 **품절이 아니라 「안 쓰기로 한 것」**이다. 재고가 들어왔다고
> `IN_SUPPLY` 로 올리면 **안 팔기로 한 상품이 되살아난다.** 주문이 들어오고,
> 아무도 왜 그랬는지 모른다.

### ★ 빠른 길과 넓은 길 ★

> 사장님: "여기에 매일 품절 상품을 적어 놓는데.. 이걸 이용해서 품절 거는게
> 더 효율적일꺼 같아" (2026-10-12)

맞다. 그 시트가 **빠른 길**이다. 둘은 성격이 다르다.

| | 품절상품 시트 (`stockouts`) | `products.status` |
|---|---|---|
| 누가 | **사람이 매일 손으로 적는다** | 이카운트 `CLASS_CD3` |
| 들어오는 길 | **시트거울 크론 30분** | 이카운트 배치 **하루 한 번** |
| 넓이 | 품절 **10건** (좁다) | 품절 **60건** (쌓인 것) |
| 성격 | **빠르다** — 적자마자 30분 | **넓다** — 빠뜨리지 않는다 |

**겹침 실측 (2026-10-12 15:00)**

| | |
|---:|---|
| **4** | 시트에만 — `JCCR00003` · `JPCR00002` · `FP220TANG0015` · `MATYG0057` |
| 6 | 둘 다 |
| 54 | `products` 에만 |
| **64** | 합 |

시트만으로는 54건을 놓치고, `products` 만으로는 **오늘 적은 4건을 하루 늦게** 안다.
**둘 다 쓰고, 회차를 시트 쪽에 맞춘다.**

### ★ 그래서 30분마다 돈다 ★

처음엔 「이카운트 배치 직후」로 잡았다. 그러면 사람이 시트에 적어도
**다음 날 아침까지 몰에서 계속 팔린다.** 그 하루가 사과 전화가 되는 시간이다.

```
시트거울 크론 (30분) ─▶ stockouts ─▶ 재고송신 (이어서) ─▶ 사방넷
```

`products` 는 하루 한 번 갱신돼도 괜찮다 — 30분마다 읽어도 같은 값이고,
바뀐 줄만 보내므로 헛걸음이 없다. **적자마자 30분 안에 14개 몰에서 내려간다.**

### ★ 입력은 둘, 결정은 한 곳 ★

0단계에서 **네 건이 어긋났다**:

| 코드 | 품절상품 시트 | `products` | 사방넷 | |
|---|---|---|---|---|
| `JPCR00002` | 품절 | 판매중 | **`IN_SUPPLY`** | **품절인데 팔린다** |
| `JCCR00003` | 품절 | 단종품 | **`IN_SUPPLY`** | **세 곳이 다 다르고, 팔린다** |
| `FP220TANG0015` | 품절 | 판매중 | `UNUSED` | 안 팔린다 — 괜찮다 |
| `MATYG0057` | 품절 | 판매중 | `UNUSED` | 〃 |

**입력이 둘인 것은 괜찮다. 결정이 둘이면 안 된다** ([[one-value-one-owner]]) —
`sabang-stock.ts` 의 함수 하나가 두 입력을 보고 **한 값**을 낸다.
화면도 cron 도 그 함수만 부른다.

### ★ 「품절예상」 5건 — 사장님 결정이 필요하다 ★

품절상품 시트에는 「품절예상」 덩어리가 따로 있다. 지금 5건이고,
**이것이 처음 문제 그대로다** — 재고 3개가 14개 몰에 떠 있다.

| 코드 | 재고 | 사방넷 | 품목 |
|---|---:|---|---|
| `MASL0123` | **3** | `IN_SUPPLY` | JH 실링 2318 (70호) 뚜껑 600개 |
| `MASL0141_3` | **5** | `IN_SUPPLY` | JH 실링 23193-6A 블랙 600개 |
| `JH2319SL0007` | **7** | `IN_SUPPLY` | JH 실링 23199 화이트 600개 |
| `BFKANSSC30001` | 3 | 없는 코드 | JH 정사각 3칸소스용기 1200개---몸통만 |
| `JHMINIJJIMB90001` | 4 | 없는 코드 | JH 미니사각찜 밀폐 23193 블랙 200개---몸통만 |

**지금 설계는 「예상」을 내리지 않는다** — 아직 파는 물건이고, 내리면 남은
3~7개를 확실히 못 판다. 그런데 안 내리면 14개 몰에서 동시에 팔릴 수 있다.

| 고를 수 있는 것 | 잃는 것 |
|---|---|
| **그대로 둔다** (지금) | 동시 주문이 들어오면 취소·사과. 세트분리가 보류로는 잡는다 |
| **「예상」도 내린다** | 남은 3~7개를 못 판다. 입고되면 5단계가 올려 준다 |
| **재고 N개 이하만 내린다** | 선을 정해야 한다 (예: 3개 이하) |

**내가 고르지 않았다** ([[leave-no-ambiguous-branches]]) — 셋 다 말이 되고,
무엇을 잃을지는 장사 판단이다. 지금은 「그대로 둔다」로 둔다.

## 4. 같은 일곱 낱말에 선이 셋 있다 — 일부러 다르다

| 선 | 어디 | 묶음 |
|---|---|---|
| 발주 판정 | `lib/product-status.ts` | 바로(판매중·품절임박) / 물어봐야(재고까지만) / 못넣음(나머지 넷) |
| 「파는 것」 인덱스 | `ix_products_sellable` | 판매중 · 판매중(재고까지만) · 품절임박 |
| **몰 판매 판정** | **이 설계** | 3장 |

**합치면 안 된다.** 「재고까지만」이 발주에서는 「물어봐야」인데 몰에서는
그냥 판다 — 쇼핑몰은 취소가 번거롭고 재고가 실시간이 아니라 남은 재고를
**쇼핑몰 몫으로 남겨 둬야** 한다 ([[stock-limited-items-mall-first]]).
협력업체 발주는 아직 우리 손 안에 있으니 미루는 비용이 훨씬 싸다.

**다른 질문에 같은 답을 강요하면 둘 중 하나가 틀린다.**

### 세트분리V2 의 잣대와는 같다

허용상태 「판매중 · 임박 · 특판」 · 부분일치
(「품절임박」→「임박」, 「판매중(재고까지만)」→「판매중」) — 3장 올리기 조건과 같은 선이다.

**재고송신의 본질이 이것이다** — 세트분리에서 보류로 빠질 상품을
**애초에 몰에서 안 팔게** 하는 것. 그러면 주문도 안 들어오고 보류도 안 생긴다.

## 5. ★ 앞으로는 「품절」과 「판매중」 둘만 쓴다 ★

> 사장님: "상태는 품절과 판매중 2개만 거의 사용할꺼야" (2026-10-12)

**재고송신에는 좋은 소식이다.** 그 둘이 곧 `OUT_OF_STOCK` ↔ `IN_SUPPLY` 다 —
가르는 규칙이 쓸 일이 거의 없어지고, 애매한 자리가 사라진다.

| 따라오는 것 | |
|---|---|
| **`특판/할인` 결정이 닫혔다** | 안 쓸 낱말이므로 v2 어휘를 여덟으로 넓히지 않는다. 「모르는 상태」 울타리만 그대로 둔다 — 0건이어야 하고 생기면 알린다 |

### ★ 짚어 둘 것 — 「재고까지만」을 안 쓰면 발주 화면의 한 갈래가 빈다 ★

지금 `lib/product-status.ts` 는 상태를 **셋**으로 가른다:
바로 넣기 / **물어봐야** / 못 넣음. 그 가운데 「**물어봐야**」에 드는 낱말은
**`판매중(재고까지만)` 하나뿐**이고, 지금 **52건**이 거기로 돌아간다.

> 「재고까지만」을 안 쓰시면 **협력업체 발주 화면의 「확인 후 알려드립니다」
> 갈래가 쓸 일이 없어집니다.** 남은 재고를 쇼핑몰 몫으로 남겨 두던 장치가
> 그 하나입니다 ([[stock-limited-items-mall-first]]).

> 그걸 접는 것인지, 「거의」에 그건 포함 안 되는 것인지 한 번만 짚어 주십시오.

## 7. 보내는 모양

```jsonc
POST /v3/sb/product/upsert
{
  "products": [          // ★ 키 이름은 products 가 맞다 (2026-10-12 확인)
    { "customProductCode": "AJ00016",   "productSupplyStatusCode": "OUT_OF_STOCK" },
    { "customProductCode": "JCCR00002", "productSupplyStatusCode": "IN_SUPPLY" }
  ]
}
```

### ★★ 두 칸만 보낸다 — 부분수정이 된다 (운영계 실측) ★★

2026-10-12, 값이 안 바뀌는 시험으로 가렸다. `JPCR00002` 에 지금과 같은
`IN_SUPPLY` 를 두 칸으로 보냈다 — `HTTP 200` · **`mode: "U"`** ·
**보내기 전후 37칸 전부 동일**.

| | |
|---|---|
| 필수 16칸 | **등록(I)에만** 걸린다. 수정은 코드 + 바꿀 칸이면 된다 |
| 보낼 대상 | **70건 전부** (16칸 왕복이면 34건뿐이었다) |
| 안전 | 상세설명 14,853자를 **다시 쓸 일이 없다.** 건드리는 칸이 하나다 |

> ★ 그래서 `전체` 모드(16칸)는 **쓰지 않는다** ★
> 코드에 남겨 두긴 했다 — 사방넷이 규칙을 바꾸는 날의 대비다.
> 하지만 그 길은 15칸을 다시 쓰므로 **훨씬 위험하다.** 기본은 `최소` 다.

> ★ `mode` 를 반드시 본다 ★ `U` 가 아니면 성공이 아니다.
> `I` 는 **없는 상품을 새로 만든 것**이고, 그래도 `status: true` 가 온다.

## 8. 바뀐 것만 보낸다

전수를 밀면 TPS 를 먹고, 무엇이 바뀌었는지도 안 남는다.
**읽기가 코드 하나씩이라 사방넷에 되물을 수도 없다** (0장).
그래서 **우리가 뭐라고 말해 뒀는지를 우리가 기억한다.**

```sql
alter table products add column if not exists sabang_status_sent text;
alter table products add column if not exists sabang_sent_at     timestamptz;
```

```
판정 함수가 낸 값 ≠ sabang_status_sent 인 줄만 보낸다
  → 성공한 건만 sabang_status_sent · sabang_sent_at 갱신
```

실패한 건은 갱신하지 않는다 — 다음 회차에 다시 대상이 된다.
**다만 같은 건이 계속 실패하면 멈추고 알린다** (9장).

> **왜 `products` 에 칸을 붙이나** — 별도 표로 빼면 조인이 생기고,
> 「이 품목을 사방넷에 뭐라고 말해 뒀나」를 두 곳에서 물어야 한다.
> 한 품목에 한 줄이고 1:1 이다. 같은 줄에 둔다.
>
> ★ 새 표를 만들면 RLS 를 같은 파일에서 켠다 ★ ([[ss-tables-had-no-rls]])

## 10. 단계 — 손실 한계

| 단계 | 하는 일 | 대상 | 틀리면 |
|---|---|---:|---|
| **0** | ✅ 끝 — 위 0장 | | 영향 없음 |
| **1** | 칸 추가 + 판정 함수 + **화면에만**(드라이런) | | 영향 없음 |
| **2** | **샌드박스**로 보내기 | | 고정 응답. 실데이터 무관 |
| **3** | 운영계 내리기, **어긋난 2건부터** (`JPCR00002`·`JCCR00003`) → **몰 화면을 눈으로 확인** | 2 | 되돌릴 수 있다 |
| **4** | 운영계 내리기 — 품절 + 단종품 + 품절시트 | **70** | 〃 |
| **5** | 올리기(`IN_SUPPLY`) 열기 — **우리가 내린 것만** | | 과판매 위험 — 2주 뒤 |
| **6** | 소싱중(3)도 내리기에 넣기 | +3 | 올리는 길이 열린 뒤라 안전하다 |

> 대상 수가 줄었다. 전수를 보니 **실제로 바뀌는 줄만** 세면 된다 —
> 품절 60건 중 사방넷이 `IN_SUPPLY` 인 31건, 단종품 80건 중 37건.
> 나머지는 없는 코드이거나 이미 `UNUSED`·`PAUSE` 라 **손대지 않는다.**
>
> 상세제작중 4건은 **전부 사방넷에 없다** — 보낼 것이 아예 없다.

**내리기가 올리기보다 안전하다.**
내리면 기회 손실(되돌릴 수 있다), 올리면 과판매(되돌릴 수 없다).
**3단계 두 건만으로도 「품절인데 팔리던 것」이 멈춘다.**

### ★ 3단계는 「보냈다」로 끝나지 않는다 ★

`OUT_OF_STOCK` 은 이 계정이 **한 번도 쓴 적 없는 값**이다 (0장).
`results[].status=true` 를 받고 끝내면, 사방넷은 받았는데 몰은 그대로인
상태를 「됐다」고 적어 둔 것이 된다 — 그러고 **68건을 밀어 버린다.**

3단계에서 두 건을 보낸 뒤 **쿠팡·스마트스토어 상품 화면을 직접 본다.**
안 바뀌면 거기서 멈춘다. 몰까지 가는 길이 따로 있다는 뜻이고,
그건 **자동화 서비스**(아직 금액도 못 받았다) 쪽 이야기일 수 있다.
