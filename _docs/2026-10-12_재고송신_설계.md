# 재고송신 설계 — 상태값 연동 (v2 → 사방넷)

> 2026-10-12 · 규격: `사방넷_API3.0_규격.md`
> **목적** — 몰이 14개다. 재고 3개가 14개 몰에 각각 「3개 있음」으로 떠 있다.
> 동시에 팔리면 11건이 취소·사과가 된다.
>
> ★ 운영계와 **v2 저장소를 읽어 보고** 쓴 문서다. 짐작한 자리에는 그렇게 적었다.

---

## 0. 설계가 세 번 줄었다

| 처음 생각 | 실측 뒤 |
|---|---|
| 이카운트 재고를 읽어 **BOM 역산**으로 세트 가용수량 계산 | **필요 없다.** 상태값이 이미 있다 |
| 옵션(단품) 레벨에 `stockQuantity` 밀기 | **필요 없다.** `stockUseYn="N"` 이라 재고관리를 안 쓴다. 상품 레벨 상태만 오간다 |
| GAS 허브가 상품정보시트를 읽어 보낸다 | **안 된다.** 그 시트는 이미 무리가 온다 ([[dont-route-through-the-product-sheet]]). **v2 가 이미 가진 값**을 쓴다 |

**남은 일은 「상태값 하나를 옮기는 것」뿐이다.**

## 1. 구조 — 상품정보시트를 «한 번도 더» 읽지 않는다

```
상품정보시트  ──(이미 있는 미러)──▶  v2  products.status
 (이카운트 배치 직후)                      │
   _productsV2Mirror.gs                   │  ★ 신규: 바뀐 것만
   → /api/products/ingest                 ▼
                              sabang.php @ 222.122.39.14
                                          ▼
                              POST /v3/sb/product/upsert
```

### 왜 v2 에서 도나

| | |
|---|---|
| **시트 부하 0** | `products` 표는 이미 채워져 있다. 시트를 다시 안 읽는다 |
| **GAS 트리거 0** | 트리거는 18개까지인데 거의 찼다 ([[gas-trigger-slots-reserve-two]]) |
| **방향이 맞다** | [[full-migration-to-v2]] — 새 일은 v2 에 둔다. GAS 에는 버티게 하는 것만 |
| **중계기 재사용** | v2(Vercel)도 발신 IP 가 유동이라 중계기가 필요하다 — **이미 있다.** 토큰만 맞으면 누가 불러도 된다 |

### 미러가 보내는 칸 — 이름이 맞는지 확인했다

`_productsV2Mirror.gs:188` 이 보내는 것과 `/api/products/ingest` 가 받는 것이 같다:

```
ecount_code · item_name · status ← 이것 · stock_qty · supplier_name · warehouse
                                   (retail_price·purchase_price 는 값 있을 때만)
```

> **미러는 「이카운트 배치 직후에만」 돈다** — 그래야 `updated_at` 이
> 「이카운트에서 받아온 시각」과 같은 뜻이 된다.
> 재고송신도 **그 미러 뒤에 이어서** 돈다. 따로 돌면 옛 상태를 보낸다.

### v2 에 낼 자리 — 이미 있는 본을 따른다

```
app/src/app/api/cron/sabang-stock/route.ts     ← 새로
sql/NNN_sabang_stock_cron.sql                  ← cron.schedule 등록
```

`sheet-mirror` · `daily-archive-pull` · `shadow` 가 전부 이 모양이다.

## 2. 상태 매핑 — ★ v2 가 받는 일곱 가지는 이것이다 ★

`sql/45_products_real_vocabulary.sql` 의 `products_status_check`.
괄호는 **2026-09-09 에 3,499줄을 세어 본 실제 건수**다.

| v2 `status` | 건수 | 사방넷 `productSupplyStatusCode` | 왜 |
|---|---:|---|---|
| 판매중 | 3,098 | `IN_SUPPLY` | |
| **품절임박** | **156** | **`IN_SUPPLY`** | **아직 판다.** 「품절」로 뭉개면 안 판다고 읽힌다 |
| 품절 | 83 | **`OUT_OF_STOCK`** | **이것이 본목적이다** |
| 소싱중 | 58 | 손대지 않음 | 아직 안 들어왔다 |
| 단종품 | 54 | 손대지 않음 | 사람이 접기로 한 것 |
| 판매중(재고까지만) | 45 | `IN_SUPPLY` | 「쇼핑몰이 먼저」 ([[stock-limited-items-mall-first]]) |
| 상세제작중 | 4 | 손대지 않음 | 곧 판다. 아직 상세페이지가 없다 |

`ix_products_sellable` 인덱스가 이미 `판매중 · 판매중(재고까지만) · 품절임박` 을
「파는 것」으로 묶어 두었다. **우리 쪽이 이미 그렇게 나눠 뒀다** — 그 선을 그대로 쓴다.

### ★ 앞 판에서 내가 두 군데 틀렸다 ★

| 내가 썼던 것 | 실제 |
|---|---|
| 「임박」이 일곱 가지에 없다 | **있다.** `품절임박` 156건. 세트분리 허용상태 '임박' 이 여기서 온다 |
| `특판/할인` 이 일곱 가지에 있다 | **없다.** v2 는 그 낱말을 안 받는다 (아래) |

### ★ 어긋난 낱말 둘 — 대기 중인 사고 ★

`moveToEcount.gs:243-244` 의 **폴백** 분기가 v2 어휘에 없는 말을 만든다:

| GAS 폴백 | v2 | 그러면 |
|---|---|---|
| `특판/할인` (CLASS_CD3 9005) | 없다 | ingest 가 `unknown` 으로 세고 **그 줄만 안 들어온다** |
| `상세제작종` (9006) | `상세제작중` (**중**) | 〃 |

**지금은 안 터진다** — 「상태」 탭(`statusMap`)이 폴백보다 우선하고,
9/09 에 `상세제작중` 이 4건 있었던 것이 그 탭이 「중」으로 적혀 있다는 증거다.
`특판/할인` 은 그날 **0건**이었다 (일곱 가지 합 3,498 = 전체).

**터지는 날** — statusMap 에 9005·9006 이 없는 품목이 생기면
그 품목은 v2 에 안 들어가고, 재고송신 대상에서도 **조용히 빠진다.**
팔리지 않을 물건이 14개 몰에 남는다.

> 고치는 자리는 **한 곳**이다 ([[one-value-one-owner]]) —
> 「상태」 탭에 9005·9006 을 넣거나, 폴백 낱말을 v2 어휘에 맞추거나.
> **둘 다 하면 또 두 주인이 된다.** 0단계에서 어느 쪽인지 정한다.

### 세트분리V2 의 잣대와 같은가

세트분리V2 설정 `허용상태: '판매중,임박,특판'` · 판정은 **부분일치**
(「품절임박」→「임박」, 「판매중(재고까지만)」→「판매중」).

**재고송신의 본질이 이것이다** — 세트분리에서 보류로 빠질 상품을
**애초에 몰에서 안 팔게** 하는 것. 그러면 주문도 안 들어오고 보류도 안 생긴다.

## 3. ★ 손대지 않는 것 — 두 겹으로 막는다 ★

### ① 우리 상태 기준

`단종품` · `소싱중` · `상세제작중` 은 **사람이 뜻이 있어 정한 것**이다. 보내지 않는다.

### ② 사방넷 현재 상태 기준

`productSupplyStatusCode` 가 가질 수 있는 값 (2026-10-12 실측):

| | |
|---|---|
| `WAITING` 대기중 · `PAUSE` 일시중지 · `UNUSED` 미사용 · `DELETE` 삭제 · `NO_DATA` | **손대지 않는다** |
| **`IN_SUPPLY` 공급중** ↔ **`OUT_OF_STOCK` 완전품절** | **이 둘 사이만 오간다** |

> 실측에서 `AJ00015` 가 `UNUSED` 였다. **품절이 아니라 「안 쓰기로 한 것」**이다.
> 재고가 들어왔다고 `IN_SUPPLY` 로 올리면 **안 팔기로 한 상품이 되살아난다.**
> 그 뒤로 주문이 들어오고, 아무도 왜 그랬는지 모른다.

**두 겹이 필요한 까닭** — ①만 있으면 사방넷 쪽에서 사람이 내려둔 것을 덮는다.
②만 있으면 우리 쪽 단종품을 건드린다. 둘 다 통과한 것만 보낸다.

## 4. 보내는 모양

```jsonc
POST /v3/sb/product/upsert
{
  "products": [
    { "customProductCode": "AJ00016", "productSupplyStatusCode": "OUT_OF_STOCK" },
    { "customProductCode": "JCCR00002", "productSupplyStatusCode": "IN_SUPPLY" }
  ]
}
```

`customProductCode` 가 **우리 이카운트 품목코드 그대로**다 (실측 확인).
`products.ecount_code` 와 같은 값이라 매칭표가 없다.

### ★ 보낼 칸만 보낸다 ★

> [수정 시 필드 처리] 필드 **누락/`null` 은 컬럼 미수정**, `""` 은 **컬럼 클리어**

`productSupplyStatusCode` 하나만 넣고 나머지는 **키 자체를 뺀다.**
빈 문자열을 「값 없음」으로 보내는 손버릇이 여기서는 컬럼을 지운다.

> ingest 라우트가 이미 같은 함정을 겪었다 —
> 「단가를 null 로 채워 보내면 9/8 에 옮겨 둔 매입가가 통째로 지워진다」.
> **보내온 것만 넣는다**는 규칙이 여기서도 그대로다.

### ★ `optionInfo` 는 «넣는 길을 두지 않는다» ★

옵션을 안 보내면 `optionEditCode` 가 작동할 일이 없다 —
`MODIFIABLE` 로 그 상품의 옵션이 **전멸하는** 사고의 입구를 막는 가장 확실한 방법이다.
설정으로 열어 두지 않는다. 코드에 그 키가 없어야 한다.

### 묶음·속도

1회 5,000건 · TPS 10(실측) · 버스트 없음 → 동시 호출 하나로 묶는다.
응답 `206` 부분성공 + `results[]` (건별 `status`·`errorMessage`).

## 5. 바뀐 것만 보낸다

전수를 밀면 TPS 를 먹고, 무엇이 바뀌었는지도 안 남는다.

`products` 에 **「사방넷에 마지막으로 보낸 상태」를 둘 칸이 아직 없다.** 새로 만든다:

```sql
alter table products add column if not exists sabang_status_sent text;
alter table products add column if not exists sabang_sent_at     timestamptz;
```

```
status 에서 계산한 보낼 값 ≠ sabang_status_sent 인 줄만 보낸다
  → 성공한 건만 sabang_status_sent · sabang_sent_at 갱신
```

실패한 건은 갱신하지 않는다 — 다음 회차에 다시 대상이 된다.
**다만 같은 건이 계속 실패하면 멈추고 알린다** (아래 가드레일).

> **왜 products 에 칸을 붙이나** — 별도 표로 빼면 조인이 생기고,
> 「이 품목을 사방넷에 뭐라고 말해 뒀나」를 두 곳에서 물어야 한다.
> 한 품목에 한 줄이고 1:1 이다. 같은 줄에 둔다.

## 6. 가드레일

| 검사 | 막는 사고 |
|---|---|
| **미러 신선도** | `products.updated_at` 이 오래됐으면 보내지 않는다. 옛 상태를 미는 것이 제일 위험하다 |
| **변동 건수 상한** | 한 회차에 전체의 N%(예 20%)를 넘겨 바뀌면 **멈추고 알린다** — 미러가 깨진 날이다 |
| **상태 화이트리스트** | 2장 표에 있는 낱말만. 3장 두 겹 |
| **모르는 상태** | ingest 가 이미 `unknown` 을 세어 돌려준다. **그 숫자가 0 이 아니면 알린다** (2장 ★) |
| **매칭 실패** | 사방넷에 없는 `customProductCode` 는 건너뛰고 목록에 올린다. **새 상품을 만들지 않는다** |
| **`optionInfo` 봉인** | 4장 |
| **운영계 쓰기 잠금** | 중계기 `allowProdWrite` — 샌드박스로 돌려 본 뒤 사람이 켠다 |

## 7. 단계 — 손실 한계

| 단계 | 하는 일 | 틀리면 |
|---|---|---|
| **0** | 8장 확인 · 어긋난 낱말 둘 정리 · `sabang_status_sent` 칸 추가 | 영향 없음 |
| **1** | 보낼 것을 **화면에만** (드라이런) | 영향 없음 |
| **2** | **샌드박스**로 보내기 | 고정 응답. 실데이터 무관 |
| **3** | 운영계 **내리기만**(`OUT_OF_STOCK`), 품목 몇 개로 | 되돌릴 수 있다 |
| **4** | 운영계 내리기 전체 (품절 83건) | 〃 |
| **5** | 올리기(`IN_SUPPLY`) 열기 | 과판매 위험 — 2주 뒤 |

**내리기가 올리기보다 안전하다.**
내리면 기회 손실(되돌릴 수 있다), 올리면 과판매(되돌릴 수 없다).
**내리기만으로 14개 몰 과판매의 대부분이 막힌다.**

## 8. 0단계에서 답해야 할 것

- [ ] **「상태」 탭에 9005·9006 이 있나** — 어긋난 낱말을 어느 쪽에서 고칠지 (2장 ★)
- [ ] `products` 의 지금 status 분포 — 9/09 수치가 한 달 지났다
- [ ] 미러의 마지막 `updated_at` — 이카운트 배치가 실제로 돌고 있나
- [ ] 사방넷 상품 중 `UNUSED`·`PAUSE` 가 몇 건인가 — 손대지 않을 대상
- [ ] 이카운트 품목 중 **사방넷에 없는** 코드가 얼마나 되나
- [ ] 사방넷 상품을 **전수로 읽는 방법** — `GET /v3/sb/product` 는 코드 하나씩만 받는다.
      TPS 10 이면 3,500건에 6분. 중계기가 받아 주면 v2 에서 돈다
- [ ] cron 자리 — 미러(이카운트 배치 직후)와 **어떻게 이어 달릴지**
