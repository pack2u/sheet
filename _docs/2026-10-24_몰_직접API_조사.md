# 쿠팡 반품/취소 — 엔드포인트 상세 (문서 전문에서)

## `GET /v2/providers/openapi/apis/api/v6/vendors/{vendorId}/returnRequests`

★ 문서가 직접 적은 경고 ★
> 「**상품 발송 전, [반품 요청 목록 조회]를 통해 '출고중지요청'이 들어온 상품은 없는지
>  반드시 확인**해 주시기 바랍니다.」
> 「고객이 출고중지요청 시(상품준비중 단계에서 반품을 접수할 경우)
>  **RU(출고중지요청) 와 UC(반품접수) 상태에서 조회**됩니다.」

**Query 파라미터**

| | |
|---|---|
| `searchType=timeFrame` | **분단위** 조회 — `createdAtFrom/To` 를 `yyyy-MM-ddTHH:mm` 으로 |
| (없으면) | 일단위 — `yyyy-MM-dd` |
| `status` | **`RU` 출고중지요청** · **`UC` 반품접수** · `CC` 반품완료 · `PR` 쿠팡확인요청 |
| `cancelType` | `RETURN`(기본) · **`CANCEL` 취소주문** — CANCEL 이면 `status`·`orderId` 를 **빼야** 한다 |
| `nextToken`·`maxPerPage`(기본 50)·`orderId` | **`searchType=timeFrame` 이면 안 쓴다** |

**조회기간 최대 31일.** 길면 타임아웃 — 짧게 권한다.

**응답 `data[]`** — `receiptId`(취소/반품 접수번호) · `orderId` · `paymentId` ·
`receiptType`(RETURN/CANCEL) · `createdAt` · `modifiedAt` ·
`requesterName`·`requesterPhoneNumber`(안심번호)·`requesterRealPhoneNumber` ·
**`receiptStatus`**:

| 코드 | 뜻 |
|---|---|
| `RELEASE_STOP_UNCHECKED` | **출고중지요청** |
| `RETURNS_UNCHECKED` | 반품접수 |
| `VENDOR_WAREHOUSE_CONFIRM` | 입고완료 |
| `REQUEST_COUPANG_CHECK` | 쿠팡확인요청 |
| `RETURNS_COMPLETED` | 반품완료 |

접수사유(`reasonCode`) 표는 문서에서 **따로 내려받는 파일**이다 (아직 안 받음).

# 반품 FAQ 에서 건진 것 (19건 중 요긴한 다섯)

### 1. 출고 직전 검문의 «열쇠»는 `RU` 다
> 「상품준비중 상태에서 반품(취소)요청 된 건들은 **`RU`(출고중지요청) 상태로 조회**가 가능합니다.
>  `UC`(반품접수) 상태로 조회 시에는 상품준비중 **및 배송지시 이후** 요청된 건들 **모두**를 조회합니다.
>  즉 상품준비중에서 요청된 반품 건들은 RU 와 UC 모두에서 **동일한 데이터**로 조회됩니다.」

→ **아직 안 나간 것만 골라내려면 `status=RU` 로 묻는다.** UC 로 물으면 이미 나간 것까지 섞인다.
  설계 2걸음(세트분리 보류)이 봐야 하는 것은 **RU 뿐이다.**

### 2. 늦으면 왕복배송비를 우리가 낸다 — 돈이 걸린 이유
> 「판매자가 출고중지요청 건에 대해 **이미출고 처리**를 하면 반품접수로 상태가 변경되며
>  이후 반품회수·반품입고·반품승인 처리가 필요합니다.
>  **이미출고 처리 시 왕복배송비를 판매자가 부담**해야 합니다.」

→ 사장님이 말씀하신 「빨리 처리 안 하면」의 **값이 왕복배송비**다.
  출고 전에 잡으면 `stoppedShipment` 로 끝. 나간 뒤면 `completedShipment` + 왕복배송비.
  **2걸음 검문이 돈을 버는 자리다.**

### 3. 직권취소·선환불은 따로 조회가 안 된다 — 칸으로 가른다
> 「직권취소되었거나, 선환불된 주문정보만을 따로 조회할 수 있는 방법은 **없습니다.**
>  다만 [반품/취소 요청 목록조회] API 로 각각의 **직권취소여부·선환불여부를 확인**할 수 있습니다.」

| 칸 | 값 | 뜻 |
|---|---|---|
| `preRefund` | Boolean | 선환불 여부 |
| `completeConfirmType` | `VENDOR_CONFIRM` | 파트너 확인 |
| | `UNDEFINED` | 미확인 (= 완료되지 않은 건) |
| | **`CS_CONFIRM`** | **CS 대리확인 = 직권취소** |
| | `CS_LOSS_CONFIRM` | CS 손실확인 |

★ 그런데 단서가 붙는다 ★
> 「'상품준비중' 상태에서 취소된 주문은 즉시환불 됩니다. 따라서
>  `completeConfirmType=CS_CONFIRM` 인 경우라도 **`cancelCompleteUser=3P_CACNEL`** 로
>  표시되는 건은 '상품준비중' 상태에서 **고객에 의해** 취소된 주문을 의미합니다.」

→ **`CS_CONFIRM` 만 보고 「쿠팡이 맘대로 했다」고 세면 틀린다.**
  `cancelCompleteUser` 를 같이 봐야 한다. (쿠팡 문서의 오타 `3P_CACNEL` 그대로 — 철자 고치지 말 것)
  → 이 두 칸을 `coupang_claims` 에 **반드시 담는다.** 뒤에 「쿠팡 탓인가 손님 탓인가」를 가르는 유일한 근거다.

### 4. 고객 철회에는 기한이 없다 — 회수 스캔까지는 계속 뒤집힌다
> 「따로 정해진 기간은 없습니다. 다만 택배기사가 고객으로부터 상품을 회수하고
>  **회수 송장 스캔을 한 시점부터는** 고객 반품/교환 철회 및 수정이 불가능합니다.
>  **그렇지만 고객센터를 통하면 회수 송장 스캔 등의 정책과 무관하게** 철회 및 수정이 이뤄질 수 있습니다.」

→ 「이제 확정됐다」고 믿을 수 있는 시점이 **없다.** 폴링을 중간에 멈추면 안 된다.

### 5. 테스트 환경이 없다 (기타문의 11번)
> 「별도의 테스트 환경이 제공되지 않으니 이점 양해 부탁드립니다.」

→ 쿠팡 쓰기 API 는 **운영에서만 시험된다.** 사방넷 때처럼
  중계기 가드를 먼저 세우고 **깨 보고 나서** 열고, 한 건씩만 보낸다.
  (사장님 기억 「운영 자료로 동시 시험 금지」·「울타리는 깨 보고 나서 믿는다」)

# 호출 한도 (기타문의 16번)
> 「쓰로틀링을 설정한 상태에서 쓰로틀링 임계치(약 90%)에 도달한 경우
>  (`X-CAG-Warnings` 로 쓰로틀링 관련 값이 전달됩니다.) /
>  `X-Extended-Timeout` 헤더를 명시했을 때 호출 횟수가 과한 경우」

→ **숫자로 된 TPS 가 문서에 없다.** 대신 `X-CAG-Warnings` 헤더를 보면 90% 에서 미리 울어 준다.
  → 중계기가 이 헤더를 **그대로 넘겨주게** 만들고, 보이면 간격을 늘린다.
